# 界面设计契约（可执行的那一份）

> 2026-09-24 立。起因：这份契约**一直只存在于对话里**——2026-09-24 做「工作模块前端优化」
> 时，全站按它扫了一遍（字号、卡片阴影、圆角、图标），但仓库里**没有一份能引用的真值**，
> 于是「按契约收口」这件事没有判据、也没法验证。这一页把它落盘，并写清**代码里的落点**。

契约的原文是参考项目（Robot Admin）那份设计说明。下面是它的条款与**本仓库对应的落点**。

---

## 1. 分层：边框，不是阴影

> "The desktop design language is tinted surfaces with restrained boundary borders
> and **no persistent shadows**."
>
> "Shadows are allowed only for modals, drawers, dropdowns, popovers, tooltips,
> or active drag feedback."
>
> 禁止项：**"Persistent shadows on cards, settings panels, tables, toolbars, or navigation."**

**落点**（`frontend/src/index.css`）：

| 类 | 规矩 |
|---|---|
| `.wb-card` | `rounded-lg` + 一圈边框，**没有 `box-shadow`** |
| `.wb-card-hover` | hover 只**强化边框**；不抬升（无 `translateY`）、不加阴影 |
| `.wb-card-hero` | 淡品牌渐变 + 边框，**没有 `box-shadow`** |
| `.wb-chip` | `rounded-md` |

**一处改，全站一起变**——所以分层规矩只写在这四个类里，不要在页面里各写各的。

**允许有阴影的地方**：模态、抽屉、下拉、气泡、tooltip、拖动反馈。判据是「它是不是浮在
别的东西上面」。页面里一个普通卡片**不是**。

---

## 2. 字号：有下限，角色固定

| 角色 | 字号 |
|---|---|
| 元信息 / 小字 | **12px（`text-xs`）——下限定在这里，不许更小** |
| 标签 | 13px（`text-[13px]`，仓库既有一档） |
| 正文 | 14px（`text-sm`） |
| 小标题 | 16–18px |
| 页面标题 | 22px |

**禁止** `text-[10px]` / `text-[11px]` / `text-[9px]`：10px 的中文在 1x 屏上认不出来。

---

## 3. 圆角：三档

`6 / 8 / 10`——即 `rounded-md` / `rounded-lg` / `rounded-[10px]`。

**禁止** `rounded-xl` / `rounded-2xl` / `rounded-3xl`。`rounded-full` 只给**胶囊**（标签、
计数徽章、头像）。

---

## 4. 语义色：一色一义

| 色 | 含义 |
|---|---|
| `sky` | **运行中** |
| `amber` | **等人**（人工卡点 / 待审） |
| `emerald` | **完成** |
| `rose` | **错误** |
| `violet` | **品牌 / 主操作** |
| `teal` | **产出** |

同一屏里同一个意思只用一种色。**改语义色要连 keyframes 一起改**——
`.wb-node-running` 本身不含颜色，颜色在 `@keyframes wb-node-pulse` 里；
只把 `bg-violet-500` 换成 `bg-sky-500` 会得到「蓝点配紫光晕」。

---

## 5. 选中态：中性面，不是品牌色

选中 = **中性面**（`bg-neutral-100` / `dark:bg-neutral-800`）。品牌色留给**主操作、焦点、
链接、真实状态**——用它标「你正停在这一项」会让一屏里出现两个主操作。

---

## 6. 图标：控件里 16px

按钮 / 输入框里的图标 `h-4 w-4`（16px）。纯装饰的大图标不受这条管。

---

## 7. 测试锚点：钉状态，不钉文案

会变的**文案**不许当断言判据；给它一个 `data-*` 锚点。已有的例子：
`data-phase`（`RunPanel` 的六态）、`data-run-panel`、`data-work-err`。

理由：「阶段」是状态、「措辞」是表达。钉文案的结果是改一句中文红一片测试，
而红的理由看起来像功能坏了。

## 8. 颜色：调色板接在 CSS 变量上（2026-10-01 换肤）

**这一条不是新增的禁令，是把已经存在的事实写下来**——在它被写下来之前，
「颜色从哪来」这件事只存在于 `tailwind.config.js` 的几行里，而任何人都可能
顺手写一句 `style={{ color: '#7c3aed' }}` 把它绕过去。

**契约**：界面上的颜色只有两个来源，其余一律不许。

| 来源 | 写法 | 什么时候用 |
|---|---|---|
| Tailwind 调色板 | `bg-violet-600` / `text-neutral-500` / `border-neutral-200/70` | **默认**。95% 的地方 |
| 皮肤变量 | `var(--wb-page-bg)` / `var(--wb-scrim)` / `var(--wb-chart-N)` | 只有「皮肤」这一层：页面底色、背景压暗层、图表色阶 |

**`violet` 这个名字现在是「强调色阶」**（语义上），`fuchsia` 与它同值。
`neutral` 是「底色与文字」。两者都接到 `rgb(var(--wb-*) / <alpha-value>)` 上，
所以**换肤不需要改任何组件**——改的是 `<html>` 上的内联变量（`src/theme.ts`）。

**禁止**：

- 组件里写死十六进制颜色（`#7c3aed`）。它不会跟着皮肤走，症状是「换个皮肤之后
  就那一处还是紫的」——而这一处永远是最不容易被发现的角落。
- 在 `index.css` 里为暗色再声明一遍同一个变量（`.dark { --wb-chart-1: … }`）。
  亮暗两套值的真相在 `src/theme/skins.ts` 的 `light` / `dark` 两份变体里，
  CSS 里那份只在「没有任何 JS」时兜底。
- 新增语义色（`--success` / `--danger` 之类）。语义色（rose=错误、amber=等人、
  emerald=完成、sky=运行）**刻意不跟皮肤走**：它们表达的是状态，不是口味。

**换肤的四层分工**（改之前先看这一眼）：

| 文件 | 职责 |
|---|---|
| `src/theme/manifest.ts` | **皮肤的格式与校验**。一份皮肤在这里就是一个对象；「只写三个字段」的推导也在这里 |
| `src/theme/skins.ts` | 内置那六个的数据。**加一个内置皮肤 = 往 `BUILTIN_MANIFESTS` 里加一条** |
| `src/theme/registry.ts` | 活的清单：内置 + 用户导入的。`listSkins()` / `skinById()` 都问它 |
| `src/theme.ts` | 设置 → CSS 变量（纯函数）+ localStorage + 写 DOM |
| `src/theme/transfer.ts` | 导入导出：一份文件 → 「会发生什么」的计划（纯函数，不碰 DOM） |
| `src/ThemeProvider.tsx` | 全局状态 + 持久化 + 后端副本 + 装/删皮肤 |
| `src/theme/background.ts` · `ThemeBackdrop.tsx` | 背景那四种模式的数据与那一张画布 |

**验证**：`npx vitest run src/theme.test.ts src/theme.contrast.test.ts src/theme.registry.test.ts src/theme.surfaces.test.ts src/AppearanceSettings.test.tsx`
（纯函数、色值对比度、格式与注册表、面板层四处都钉住了）；要看配色本身跑
`npm run preview:themes`，生成 `theme-preview.html`——**20 张（10 皮肤 × 亮暗）**
并排的缩略图，用的是同一套变量（**注意**：那份静态预览画的是皮肤数据里的
颜色与壳，不画 §8.5 之后的面板层，所以「通透度」在那张图上看不出来——
要验面板层请看 §8.5/§8.7 的验收，或者直接开设置里的皮肤中心）。

### 8.1 强调色实底：`.wb-btn-primary` 与 `.wb-accent-fill`（2026-10-01 已收口）

**按钮**一律 `.wb-btn-primary`。它承担：`inline-flex` 居中、`rounded-md`、字重、
白字、`hover:brightness-110` / `active:brightness-95`、
`disabled:cursor-not-allowed disabled:opacity-40`，以及**渐变两端来自皮肤**
（`--wb-btn-from/to`，亮色 600→700）。尺寸类留在调用处（`px-4 py-2 text-sm`），
布局类（`ml-auto` / `shrink-0` / `cursor-grab` / 固定宽高）原样保留。

**不是按钮、但也要强调色实底**的元素（logo 方块、用户头像、自己发的那条消息气泡、
占比条）用 `.wb-accent-fill`（右下渐变）或 `.wb-accent-fill-r`（向右渐变）。
它们**不套 `.wb-btn-primary`**——那个类带着 `hover` / `disabled` / 按钮盒模型一整套
语义，套在 `<div>` 上是错的（§4-7 一事一处：这里要的是「强调色实底」这一件事）。
注意它**不设文字色**：用它的元素自己带 `text-white`。

**2026-10-01 收口**：全仓 37 处手抄的 `bg-gradient-to-* from-violet-600 to-fuchsia-600`
已经全部改完（22 个文件），迁移脚本按「整串相等」逐条替换、跑完审计残留 0 处。
现在 `wb-btn-primary` 51 处、`wb-accent-fill*` 7 处。

还剩下**三处刻意保留**的写法，都不是按钮、也不该被上面两个类取代
（`designRules.test.ts` 里有一条守卫钉着它们，判据与理由都写在那条用例里）：

| 位置 | 为什么留着 |
|---|---|
| `Welcome.tsx` 首页标题 | 三停渐变**文字**（`violet→fuchsia→violet` + `bg-clip-text` + 流光动画）。它要的是「彩色字」不是「色块」，`.wb-accent-fill` 给不了 `bg-clip-text`；而它已经跟着强调色走（`violet`/`fuchsia` 都接了变量） |
| `dashboardCards.tsx` 的 `toneClasses.violet` | 那是**数据语义的五色标度**（violet/fuchsia/emerald/sky/rose 各代表一类指标），同样配 `bg-clip-text` 做渐变数字。**不能**只把其中一档换成变量——那会让五色标度里的一档是变量、另外四档是固定色 |
| `DashboardPage.tsx` 柱状图当天那根 | 它要的是**向上**的渐变（`to-t`），而 `.wb-accent-fill` 固定右下；8px 宽的柱子上换方向没意义，直接写变量反而更清楚 |

守卫的判据是「`bg-gradient` + `from-violet-`/`to-fuchsia-` 且**没有** `bg-clip-text`」——
前两处因为有 `bg-clip-text` 天然放行，第三处按文件名白名单。

**下次改按钮**：不要再手抄渐变。`docs/r-checklist.md` 里那条「不许用脚本批量改源码」
依然作数——这次的迁移脚本之所以能用，是因为它只做**整串相等**的替换、一条对不上就报错，
跑完还 `grep` 复核了一遍；模糊匹配的批量替换就是那条教训的由来。

### 8.2 皮肤是**数据**，不是代码（2026-10-02）

第一版把六个皮肤写死在 `skins.ts` 里，那意味着「加一个皮肤要改代码、重新构建」。
现在一份皮肤是一个**对象**，校验、推导、导入、导出都走同一条路。

**手写一份能用的皮肤，只要三个字段**：

```json
{ "id": "sakura", "label": "樱", "accent": "#d9558a" }
```

亮暗两套强调色、十一条色阶、中性阶、页面底色全部推出来。想细调就往上叠——
**每一项都是「写了就用写的，没写就推」**（`manifestToSkin` 是唯一的推导处）：

```json
{
  "id": "sakura", "label": "樱", "accent": "#d9558a",
  "author": "谁做的", "hint": "一句话说明",
  "light": { "pageBg": "#fdf0f5" },
  "dark":  { "accent": "#f0a0bc" }
}
```

| 字段 | 不写会怎样 |
|---|---|
| `id` · `label` | **必填**。id 只能是 `[a-z0-9][a-z0-9._-]*`，且不能叫 `constructor`/`prototype`/`__proto__` |
| `accent` | 推一个紫色兜底。给了它，暗色那一边自动提亮 28%（同一色号在暗底上会发闷） |
| `light` / `dark` | 整个变体可以不写 |
| `accentScale` | 由该变体的 `accent` 推 11 档。**要写就得 11 档全写**——少一档会出现「某个类名落到兜底值上」 |
| `neutral` | 用格式自带的那份（底色与文字是所有人的地板，不是口味） |
| `pageBg` | 由 `accent` 往白/黑推 93% / 90%（推到几乎认不出来：底色该安静） |
| `chart` | 一档中性的蓝绿黄红紫。**刻意不从强调色推**——单色阶画多序列图分不出谁是谁 |
| `hint` · `author` | 空。作者只显示在导入的皮肤卡上 |

**加一个内置皮肤** = 往 `BUILTIN_MANIFESTS` 里加一条。**加一个自己的皮肤** =
在设置 → 外观 → 导入 / 导出里贴一份文件，不用改代码、不用重新构建。
导出任意皮肤得到的就是这个格式，改两个色号再导回去就是新皮肤
（导出的中性阶与色阶**只在不是推导出来的那一份时才写**，所以手写的那份导出来仍然只有几行）。

**导入是合并，不是替换**：文件里没提到的皮肤留在本机不动。三条不变量：
内置 id 不可被顶掉；一个坏条目只跳过它自己（并说明原因）而不是整次失败；
**校验的是合并之后的结果**——装完会超过可导出上限时整次拒绝
（否则用户从此做不出备份，而他不会知道）。设置指名了一个装不上的皮肤时，
**要说出来**，不能静默退回默认。

**主题作者可以依赖的钩子**（这三个属性是契约；`dark` 那个类名不是——
它是 Tailwind 的实现细节，换一套暗色方案就没了）：

| 属性 | 取值 | 意思 |
|---|---|---|
| `html[data-wb-skin]` | 皮肤 id | 用哪套皮肤 |
| `html[data-wb-mode]` | `light` \| `dark` | **生效的**亮暗（`system` 已经解析过了） |
| `html[data-wb-bg]` | `skin` \| `solid` \| `gradient` \| `image` | 背景是哪一种 |

**明暗三档**：`light` / `dark` / `system`。出厂是 `light` 而**不是** `system`——
跟随系统是个好默认，但它是一次替用户做决定，该由用户自己点。
`system` 时 `matchMedia('(prefers-color-scheme: dark)')` 变化会实时跟随，不用刷新。
`theme.test.ts` 里有 v1（`dark: boolean`）→ v2（`mode`）的迁移用例——
`STORE_VERSION` 那个字段就是为这件事留的。

**对比度只对内置皮肤背书**：用户导入的皮肤用的是他自己填的颜色，产品没法替他担保，
所以 `theme.contrast.test.ts` 迭代的是 `BUILTIN_SKINS` 而不是 `listSkins()`——
**量不了的东西不该假装量过**。

### 8.3 图片式背景皮肤（2026-10-02）

皮肤可以自带一张底图。**与用户自定义背景只有一条规则**（`theme.ts` 的 `effectiveBg`）：
用户自己设了背景就以用户的为准；用户没设（`mode === 'skin'`）才轮到皮肤那张。
所以「恢复默认外观」自然回到皮肤自带的那张，而那句话的意思本来就是「回到这套皮肤的样子」。

内置三套：**素纸**（纸纹平铺）、**远山**（雾里四道山脊，`cover`）、**格纸**（工程方格纸平铺）。
亮暗各一张，一共 6 个 SVG、**合计 8.7 KB**。

**图片怎么来的**：是**手写的 SVG**，不是位图。理由有三条——
文本文件能在 diff 里被审阅、能跟着主题改颜色、缩放不糊。
素纸的两层纹理用 `feTurbulence`（低频云斑 + 高频纤维/帘纹），
`stitchTiles="stitch"` 是平铺的关键：没有它每一格的接缝会显出一条线。
格纸的线画在 `x.5` 上、宽 1（正好落在像素上），而且**大格线只画格子的左/上边缘**——
两边都画的话平铺之后接缝处会变成双倍粗的一条。

**压暗怎么分布**（`scrimDir`）——这是「图很美」与「字看得清」能同时成立的地方：

| 取值 | 什么时候用 | 怎么算 |
|---|---|---|
| `flat` | 默认；**平铺的纹理强制用它** | 整屏一层，滑块上是多少就压多少 |
| `edge` | 风景类（`cover`） | 文字多在左边（侧栏）和上边（顶栏），压暗往那两处堆 |

`edge` 是三条梯度合成：横向（管侧栏，`p×0.75`，到 62% 归零，其中前 30% 保留大半强度
因为侧栏占屏宽约 18%）、纵向（管顶栏，`p×0.5`，到 34% 归零）、以及一层减弱到
`p×0.25` 的**全页底子**——中间不能是零，页面标题、空状态、无卡片的列表行都直接落在图上。
滑块上那个数说的是**文字那一带**的压暗强度，不是全页的。

**平铺的纹理强制 `flat`**：图案被压得一边深一边浅，看起来不像「有明暗」，像渲染坏了。
这一条在 `parseSkinBg` 里就归一了（同时强制 `blur: 0`——糊了的图案不是朦胧，是一片脏色），
不等画的时候再判一次。

**压暗有下限 `MIN_SKIN_SCRIM = 45`**：底图上的字能不能看清，不该由皮肤作者记不记得
压一层决定。留一档兜底比事后补一条「某某皮肤看不清字」便宜得多。

**底图地址的白名单**：`/skins/...`（跟着产品发的）、`/api/images/...`、`http(s)`。
**不收 `data:`**——皮肤是数据、可能来自别人给的一份 JSON，那种值会进 `url()` 且完全不可审阅。

**验证**：`npx vitest run src/theme.bgSkin.test.ts`（分派规则、梯度形状、地址白名单、
下限、平铺归一）。**但 SVG 滤镜和背景层 jsdom 一个都不渲染**，所以「图到底画出来没有、
字压不压得住」只有真浏览器能量：起 Vite + 无头 Chrome，把 SVG 画进 canvas 读像素
（纸纹有非零 alpha、格纸有等距格线、远山有多个色带），再把图与压暗合成起来算对比度。
判据不是「≥ 4.5」而已，而是**「铺上图之后不比它替换掉的那个纯色底更差」**——
实测：纸 5.07 / 5.03、远山 4.56 / 4.73、格纸 5.16 / 5.01（亮色），
暗色一档全在 6.7 以上。亮色下铺图只会**略微**降一点（白压暗层压不亮近白的天空），
三套都仍在 AA 之上。

### 8.4 上传一张图，现做一套皮肤（2026-10-02）

**上传图片**这件事原来只有一条路：它成为一件**背景**（`bg.mode = 'image'`）——
图盖上去，强调色还是上一个皮肤的那个。一张暖橙色的日落照压在紫色按钮下面，
看起来不像一套配色，像一次事故。

现在有第二条路：**图 → 一套皮肤**。它出现在皮肤表里，可以切走再切回来、可以改名、
可以跟着导出。两条路都留着，因为它们回答的是两个问题——「我就想换个底」与
「我想让整个工作台变成这个样子」。

**入口摆在皮肤表那一格**（`data-skin-from-image`），不摆到「自定义背景」下面。
用户在这里看到的是「有哪些皮肤」，那么「再加一款」也该在这里。Warp 的主题选择器
里就是一个 `+`。

#### 只算一个数

`theme/extract.ts` 输出的只有**一个色号**（外加两个压暗百分比）。
十一条色阶、两个变体、页面底色**一个都不算**——那些已经有主了
（`accentPalette` / `resolveAccent` / `resolvePageBg`），重复一份就是开第二个真相。
所以生成的皮肤数据只写 `accent` 与两个变体的 `bg`，其余留空交给推导。

> **2026-10-03 补**：这只说对了一半。§8.5 之后，「一整套皮肤」还需要**面板层**
> 与**色调**，而它们也该从图里来——否则得到的仍然是一张壁纸。
> 见下面「一张图 → 一整套皮肤」。

取色这一段是**照着成熟实现来的**（color-thief 与 node-vibrant 的 MMCQ）：
画小再读像素（128×128，一张 4000×3000 直接 `getImageData` 是 45MB 的数组）、
两段式中位切分（先按数量切到 3/4，再按「数量 × 跨度」切到底）、
按 `√占比 × 饱和度 × 明度` 打分。**没有自己发明一套**——那些常数是调出来的。

三条自己加的规矩：

- **`√占比` 而不是占比**：color-thief 的 `getColor()` 返回最大的那一簇，于是在任何
  截图或白底商品图上取到的都是背景色。占比开方之后，一个小而鲜艳的东西能赢过
  一大片灰的，但赢不了太多。
- **滤掉接近纯白的像素**，并用一条**逐级放宽的阶梯**兜底（全被滤掉时退回全部像素）：
  一张全白图不该因为「把白色滤掉了」而一个候选都不剩。
- **无彩色就不编色相**：一张黑白照片取到的是它的平均灰，界面明说「这张图没有颜色」。
  编出来的色相没有出处，用户没法理解也没法复现。

#### 压暗是**算出来的**：三个位置，各取各的最不利像素

这是这一节最要紧的一段，因为它的第一版是**错的**。

文字实际压在什么上，取决于**三件事**：这一处叠了几层压暗、壳在那上面盖了什么、
屏幕上是哪一块。

| 位置 | 屏幕上的哪一块 | 压暗层 | 壳自己的底色 | 那一处的字 |
|---|---|---|---|---|
| 侧栏 | 左 20% × 全高 | `sideMid + base` | 70% 白 | `neutral-500` |
| 顶栏 | 全宽 × 上 8% | `top + base` | 85% 白 | `neutral-500` |
| 主栏顶部 | 左 20%–35% × 上 8%–20% | `sideMid + top + base` | — | `neutral-500` |

前两格的 **`CHROME_VEIL`** 是关键：侧栏与顶栏自己就是半透明的（`Layout.tsx`），
字压在它们上面时，底下那层图已经被它们自己又洗白了一遍。**不算这一层，一张中间调的
图会被解出 80% 的压暗**，而算上之后是 45% 上下——差别正好是「图还在」与「图没了」。
它是壳的结构在主题系统里的一份投影，所以 `designRules.test.ts` 把两边那几个数字
钉在一起（改 `Layout.tsx` 的 `bg-white/70` 会让主题那边的守卫红一次）。

**每一处各取各的最不利像素**，不是全图取一个再套到所有地方。第一版就是后者，
而它错得很具体：一张「上面亮、左下角暗」的风景照，左下那块暗只压在侧栏上
（侧栏有 70% 白底兜着），拿它去要求**没有壳底色**的主栏顶部，等于凭空多要一大截压暗
——多要的那一截全花在了图上。取 5% / 95% 分位而不是极值：一个像素的黑点不该把全图压死。

#### 够不到目标时**不往死里压**

扫描 `p` 找第一个让三处全过的值；找不到时停在 **62%**（`FALLBACK_SCRIM` =
`DEFAULT_BG.scrim`，内置图片皮肤用的那一档），**不是 95**。

这是量出来的，也是被截图抓住的：一张「上亮下暗」的风景照从 62% 压到 95%，
只把侧栏那一处从约 3.95 抬到 4.43——差 0.5，而代价是那张图彻底看不见了
（亮色模式下就是一片白，而用户上传那张图正是为了看到它）。
目标够不到的时候，继续加压几乎买不到对比度，却把图整片吃掉。

于是 `scrimForImage` 返回三个东西：`scrim`、`ok`，以及压到那一档时**实际**能到的
对比度 `ratio`。界面把 `ratio` 摆出来（「最不利的一处约 3.89:1，AA 要 4.5」），
说清「再往下压这张图就看不见了，所以没有继续压」，并给一个**一键切到另一个明暗模式**
的出口——同一张图在那边要的是相反的方向，往往正好合适。

这条规则有一道硬边：`ok` 为真时压到够为止（可能到 95%），为假时停在 62%。
两侧看起来会跳（130 的灰停在 62%、140 的灰压到 95%），但那正是「再压也买不到对比度」
的实情，不是连续的。

#### 有意留着的两处取舍

- **页面中段（远离左右边缘、远离顶部）不参与求解**。那里的正文都在卡片里
  （卡片不透明），露在背景上的只有空状态与首屏那几句。按 `neutral-500` 要求那一块的话，
  任何一张中间调的图都得压成一片白，而那等于把「换一张图」这件事取消掉。
  代价是**首屏那几行小字在花样照片上会偏淡**——已知、有界，用「这个模式托不住这张图」
  那句话兜着。要修的话该修的是那几句文案自己的底，不是把图压死。
- **名字与出处来自文件名**（`labelFromFilename`），改名的入口在皮肤卡上（铅笔）。
  改名**必须走 `parseSkin`**：`installUserSkins` 信任调用方，从那里塞一个 40 个字的
  名字会被原样存下来，而下次打开时 `loadUserSkins` 逐条 `parseSkin` 会把它丢掉——
  症状是「改完名字，刷新之后这个皮肤没了」。

#### 导出**不带图**

皮肤 JSON 里只有图的地址（`/api/images/...`），图片本身留在 `data/images/`。
参考实现里 Warp 的主题仓库明确拒收二进制底图（「只收 yaml」），理由一样：
导出是设置档案，不是照片备份。所以一份导出的图片皮肤拿到另一台机器上，
图不在那儿——`ThemeBackdrop` 探到图加载不出来就整层不画，皮肤退回自己的页面底色，
仍然是一套能用的皮肤（`accent`、色阶、亮暗都在）。**保留那个条目、退到一个能看的
默认样子，绝不悄悄删掉用户起过名字的东西。**

#### 验证

- 纯的那两半（中位切分、挑色、算压暗）在 `src/theme.extract.test.ts` 里，
  31 条。对比度**自己算一遍**，不复用 `color.ts` 的 `relativeLuminance`——
  测试要能独立地量出生产代码算错了。最要紧的一条是「**它说够了就是真的够了**」：
  自己把三层合成出来，量一遍三处，看是不是真的 ≥ 4.5。
- **读像素那一半 jsdom 跑不了**（没有 canvas，图片也不会 load），只能真浏览器：
  起 Vite + 后端 + 无头 Chrome，真上传三张图（暖色黄昏 / 夜景 / 灰阶），
  走真界面点「用图片做一款」，再从**截屏的像素**上量侧栏压在图上的实际对比度。
  43 条全过。**量之前要先把字藏起来**（`color: transparent`）：文字区里最暗的像素
  就是字本身，直接取极值量到的是「字压字」，会得到 1.95 这种没有意义的数。
  实测与算出来的对得上：暖色黄昏那张，模型 3.89、屏幕上量到 3.98。
- 一遍真浏览器验收还顺带证了一件事：主题的**后端副本是真的会回读的**——
  上一次跑完停在暗色，崭新的浏览器配置打开也是暗色（「换台机器打开也还在」）。
  验收脚本因此要先把起点写成确定的一份，否则每条断言都在依赖上一次跑剩什么。

### 8.5 分区域的面：从「主题」到「完整皮肤」（2026-10-03）

§8.4 之后，一套皮肤能决定的仍然只有**背景 + 配色**。卡片、侧栏、顶栏、输入框、
下拉的底色全都是写死的（`bg-white` 169 处、`dark:bg-neutral-900` 之类的 325 处），
皮肤改不动它们——所以「换了一套皮肤」在观感上仍然只是「换了一张壁纸 + 换了按钮颜色」。
社区里那些 Codex 换肤项目做的不是这件事：它们让**背景、面板、壳、边框、强调色
一起构成一个视觉体系**（背景是氛围，面板是承托，字是结果）。这一节补的就是面板。

#### 四个区域，一个旋钮

皮肤数据里多了一个 `surfaces`，它只有五个数：

| 旋钮 | 管什么 | 不写时 |
|---|---|---|
| `glass` | **卡片 / 面板**的不透明度 0–100 | 100（实心） |
| `chromeGlass` | **侧栏与顶栏**的不透明度 | 85 |
| `blur` | 面板与壳的 `backdrop-filter` px | 0 |
| `borderAlpha` | 结构性边框的浓度（下限 55） | 100 |
| `shadow` | **浮层**阴影强度（卡片永远没有常驻阴影） | 100 |

输入框与浮层的不透明度**不给旋钮**，由 `glass` 推并各自有下限（80 / 95）。
`theme/surfaces.ts` 里那张 `PANEL_FLOOR` 表是这一层的核心：

```
card 55    field 80    float 95
```

**下限不是审美，是「能不能用」**：全透的卡片不是通透，是「没有卡片」；浮层透了
就是两层字叠在一起。参考实现里踩过这个坑（面板一透，底下滚动的内容就穿上来），
所以这三条在 `panelAlpha()` 里兜，作者改不动。

#### 一处也没有手写：全局只加了一个类

| 层 | 谁消费 | 变量 | 改了几处 |
|---|---|---|---|
| 卡片 / 面板 | `.wb-card`（145 处用它） | `--wb-surface*` | **1** |
| 壳 | `.wb-chrome`（侧栏 + 顶栏） | `--wb-chrome*` | **2** |
| 浮层 | `[data-wb-skin] .wb-float`（11 处） | `--wb-surface` + `--wb-float-alpha` | **11 行插一个类名** |
| 输入框与其余面板 | `[data-wb-skin] .bg-white` / `.bg-white\/NN` | `--wb-surface*` | **0** |

最后一行是这一节最省事的一条：`bg-white` 在这个仓里**语义上就是「面板底」**
（169 处全是卡片、输入框、下拉、气泡），所以按属性覆盖它的 `background-color`
就够了，组件一个都不用改。

**只改 `background-color`，不碰 `color` 与 `border-color`**：`text-white`（57 处）
是**压在实底上的字**，`border-white/15`（13 处）是**压在深色面上的浅色叠层**——
它们和「面板底」共用 `white` 这个名字，语义却完全不同。整条 remap `white`
会把那 70 处一起改掉，其中大半没有 `dark:` 配对，暗色下会变成「深色字压在深色按钮上」。
**同一个名字，三种意思，所以只能按属性切，不能按名字切。**

#### 背景层也跟着长：取景、色调

`ThemeBg` / `SkinBg` 多了四项，都只在图片模式下有意义：

- **`focusX` / `focusY`**（焦点）与 **`zoom`**（缩放 100–250%）。一张竖图铺在宽屏上，
  默认的居中裁切会把要露的东西切掉——这类「图选对了、位置不对」的抱怨，
  修法是给两个数，而不是给一个裁剪工具。缩放用 `transform: scale()` 而不是
  `background-size`：后者在 `cover` / `contain` 下是关键字，乘不了一个倍数。
- **`opacity`**：把图**淡出**到页面底色上（与「往图上盖一层」的压暗方向相反）。
- **`tint`**：图与压暗层之间的**一层色调薄纱**。压暗是**可读性**机制（颜色由明暗
  模式定死、强度按图算出来），色调是**风格**机制（一层深海蓝、一层暖褐）。
  顺序不能反：色调在压暗**下面**，否则皮肤随手改一个色调就会把「字读不读得清」
  一起改掉，而那是这一整套里唯一不能被风格牵着走的东西。

于是一个微缩的工作台有六层可画：底图 → 色调 → 压暗 → 侧栏/顶栏 → 卡片 → 输入条。

#### 预览是**现画的**，不是缩略图

`SkinPreview` 按皮肤自己的色值画一个微缩工作台（`SkinPreview.tsx`），
「当前皮肤」那块大的与皮肤库里每张小卡**用的是同一个组件**。
两处各画一套的话，小卡上看着通透、切过去发现不透，而那种不一致正是
「预览」这个词最不该出的错。

它读的是**皮肤数据**而不是 CSS 变量：皮肤库里要同时摆十几套，而同一时刻只有一套
生效——读变量的话所有卡都会画成当前那一套，「预览」就成了笑话。
大预览那条路例外，它**跟着用户覆盖走**（拖滑块立刻变），所以它画的是 `resolved`。

#### 两个界面上的决定

- **「恢复原始界面」挨着当前皮肤，不藏在角落。** 它只动外观设置，**不动导入的皮肤**
  ——那句话说的从来是外观，不是「清空我装过的东西」。
- **「存成新皮肤」存的是生效值**，不是「皮肤 + 覆盖」。用户拨出来的这一套就是他
  想要的那套，而一份「皮肤 + 三个覆盖项」换台机器打开时，任何一个覆盖项丢了都会
  变成另一套外观。存完覆盖让位（写进皮肤数据了，留着就是两套说法）。

#### 有意留下的两条

- **素纸与格纸没给 `surfaces`**（仍然是实心面板）。它们是**平铺纹理**，
  压在半透卡片下面看不见，透了只会让字变模糊。例外写进了 `theme.bgSkin.test.ts`，
  免得下次有人以为漏了。
- **壳的两个透明度统一成了一档**（原来侧栏 70、顶栏 85）。两个数不一样是历史遗留，
  不是设计，而换肤要求「壳」是一个可命名的区域。默认 85 在无底图时看不出来
  （差 4/255），有底图的那两套皮肤各自声明了自己那档。

#### 验证

- 纯的那一半在 `theme.surfaces.test.ts`（12 条）：四档面的下限、底色的推导方向、
  导出往返。「**拨不坏**」是重点——一份写着 `glass: 0` 的皮肤导入进来，
  卡片仍然是 55%。
- CSS 那一半 jsdom 一个都算不出来，所以还是真浏览器：起 Vite + 无头 Chrome，
  读**计算样式**（卡片底的 alpha、壳上的 `backdrop-filter`、色调层的 `rgba()`、
  `background-position`），34 条全过。拦下来的两个真 bug：
  1. `fillSurfaces()` 把默认值 `surface: ''` 补进运行时对象，`skinToManifest` 又把它
     写进导出文件——而解析器把空串当坏值，于是**一份自己导出的皮肤导不回来**。
  2. 「存成新皮肤」取的是皮肤那一份值而不是**生效值**，于是拨到 40 再存，
     存下来的还是 82——而界面上明明写着「存的是现在生效的这一套」。
- **`preview:themes` 那个静态预览没有跟上这一层**（它只画颜色与底图）。
  那是开发者用的离线快照，真正的预览是应用里的皮肤中心，不值得为它再实现一遍
  面板模型；写在这里免得有人拿它去判断通透度。

#### 三个 Codex 换肤项目各自做对了什么（以及哪一部分不该抄）

调研记在 `research/codex-skin-research.md`（实地读了 **Codex Dream Skin**、
**黑哥 Codex Skin Studio**、**awesome-codex-skins** 的源码与真实主题包；
「codex-skin」这个名字**在任何可达索引里都不存在**，它是中文文章里对这类工具的
通称，不是仓库名——记在这里免得下一个人再去找一遍）。

**三家独立收敛到同一套架构**，而那套架构**不是** CDP 注入那部分：

> 一个小的 token 层 + 一组**封闭的、有名字的区域接缝** + 按区域覆盖的白名单 +
> **结构化的一键还原**。

| 它们做的 | 这里怎么落 |
|---|---|
| 区域是**封闭枚举**（DreamSkin 硬编码 12 个 `[data-ds-part]`，语法只允许一条规则一个部件） | `index.css` 里那五条：`.wb-card` / `.wb-chrome` / `.wb-sidebar` / `.wb-topbar` / `.wb-float` |
| 接缝用 **`data-*`**，不用哈希类名（`[data-ds-part]` 活下来了，`_ComposerLayoutRoot_` 每个版本都断） | `[data-wb-skin]` 作用域。**去掉这个属性 = 一次全还原**，与它们那句「single-class full reversal」是同一个性质 |
| 直接覆盖**宿主自己的 token 层**（HeiGe 只用 6 行） | 整个系统从第一版起就是这条（`tailwind.config.js` 把调色板接到 `--wb-*` 上） |
| **导入一份皮肤不该压掉 last-known-good** | 「恢复原始界面」只动外观设置，**不动导入的皮肤**（§8.2 已定） |

**明确没抄的**（都是「不拥有那个应用」的税）：CDP / 调试端口 / asar / 代码签名、
那一整套选择器漂移装置（`selectors.json`、兼容档案、`doctor`）、
把 `config.toml` 与计划任务写进用户机器、把 1.4 MB 的图 base64 进 `data:` URL、
以及把「重命名宿主品牌」当卖点。**这里的 CSS 是自己的，markup 就是契约。**

**被它们改掉的两个数**：

- **模糊上限从 40px 收到 24px。** HeiGe 把侧栏 20→8px、气泡 22→8px（源码原话
  「大半径模糊会逐帧重采样」「大模糊是卡顿主因」），awesome-codex-skins 整套只用
  2/4/6px，DreamSkin 的允许集上限 30px。实测分布是「内容 4–8px、壳 14–20px」。
- **换掉「背景图用 `background-attachment: fixed`」这条捷径。** HeiGe 的源码里
  有一条注释：「不用 fixed 背景附着：流式输出/滚动时会强制整视口逐帧重绘」。
  这里用的是 `position: fixed` 的独立图层（`.wb-backdrop`），本来就没走那条路——
  写下来是因为「把 fixed 换成 background-attachment」看起来像是同一件事的简化。

**它们指出、而这里已经做对的**：预览**现画**比截图强（DreamSkin 的 README 专门
警告仓库里那几张概念图「绝不能当背景导入」；awesome-codex-skins 则把预览做成
**CI 卡着的构建产物**，明令「concept art 不算」）——这里的 `SkinPreview` 从数据现画，
没有「缩略图与真实配色分叉」这条路可走。

**一条还没做、但值得记的**：HeiGe 的**阅读增强**（回复区 90% 半透明 + **完全不用
模糊**，默认开、可关）。它解决的是「长对话里气泡盖在滚动内容上」这一类问题；
这里对应的是 `.wb-float` 与输入框的**下限**（95 / 80），思路一样
（可读性用不透明度兜，不用模糊兜），只是还没做成一个用户能开关的档。

### 8.6 一张图 → **一整套**皮肤（2026-10-03）

§8.4 把「上传一张图」做到「取一个强调色 + 按图算压暗」。§8.5 之后那还不够：
面板、壳、色调都已经是皮肤的一部分了，而它们**也该从这张图里来**——
不然「一张图生成一套皮肤」这句话只兑现了一半（拿到的是壁纸，不是皮肤）。

现在 `deriveSkinColors` 除了颜色还量**两个统计量**，并由它们推出整套面板层：

| 量什么 | 怎么量 | 推什么 |
|---|---|---|
| **有多花** `spread` | 亮度 **5%–95% 分位之差** | `glass`：图越花面板越实（`[70, 88]`） |
| **有多密** `detail` | **相邻采样点亮度差的均值** | `blur`：细节越密越糊（`0–14px`） |
| （托不托得住） | §8.4 已经算过的 `okLight` / `okDark` | **明暗倾向**：亮色能用就用亮色 |

三条都能单独说清楚为什么：

- **分位差而不是极值**：与压暗那边同一条纪律——一个像素的黑点不该代表整张图。
  实测四张标定图：雾 0.12 / 密纹 0.66 / 黄昏 0.77 / 夜景 0.21。
- **明暗拉得越开越实**：一张对比强烈的图，卡片透出来就是字与图打架；
  一张本来就平的图（雾、纸、单色），透一点什么也不会发生。
  区间两端都不到 100——**一张图当背景的皮肤，面板实心了就白搭了那张图**。
- **`detail` 这条规则没有先例**，是我们自己定的：调研的三个成熟实现都按**帧率**
  而不是按图来定模糊。所以它写得尽量直白，而且**只当默认值**——
  效果卡上那根滑块随时能改。它量的是「尺度在图像宽度 1% 以上的结构」，
  更细的东西在 128 宽的缩略图里已经被平均掉了：那是**读像素那一步**丢的，
  不是这里算错的（一张 4×4 的噪声在屏幕上确实就是一块均匀的灰）。

**色调的方向按模式定**：亮色往白里推、暗色往黑里推。这不是审美——色调层在压暗层
**下面**，而压暗是按**原图**解出来的；色调要是反过来把图压暗（亮色模式下），
解出来的压暗就不够了，而「字读不清」是这一整套里最不能出的问题。
往压暗那一头推，色调取什么色都安全。无彩色的图**不叠色调**（一层灰纱只让画面发闷）。

**明暗倾向只按一件事判**：`scrimForImage` 量出来的「托不托得住」。
不去「猜图是亮是暗」——亮度与「能不能当某个模式的背景」不是一回事
（一张亮但对比强烈的图，暗色下反而好看），而已经量出来的结论比自己再猜一遍准。
于是流程里那条规则很短：**当前这个模式托不住、而另一边托得住 → 直接落过去**，
并说清是顺手切的。两边都好时不替他选（他可能特意开着跟随系统）。

#### 两个被验收抓出来的错

1. **`tint: { color: '', alpha: 0 }` 让生成的皮肤装不上。**
   `DEFAULT_TINT` 就是那个空串（= 没有色调），生成器把它原样写进数据，
   而解析器把空串当坏值——报的还是「color 要写成 `#rrggbb`」，与看到的空字符串
   对不上号。**与 `surfaces.surface` 的空串是同一个坑**（那次修了那一处，漏了这一处）。
   两处现在都按「空串 = 没写」处理；生成器那边也改成「没有色调就整项不写」——
   不写就是没有，这条最短。
2. **`blur` 的系数估错了一个数量级，整段推导成了死代码。**
   原以为照片的相邻差均值落在 0.02–0.06，实测是 **0.001–0.002**——
   128 宽的缩略图把相邻像素的差都平均掉了。拿错的数量级去乘，**每一张图都算出 0px**。
   改成以一张有名有姓的标尺（`TYPICAL_DETAIL = 0.003`，一张普通照片）为参照：
   它给 5px，比它平就少糊、比它密就多糊。用比值而不是固定系数，是因为
   「多密算密」只能相对一个参照物说。
   两件事都是**浏览器验收**抓到的——四张图的 blur 全是 0 这种症状单测里看不见
   （单测喂的是自己造的样本，而样本的 detail 正是按那个错的数量级造的）。

#### 验证

- 单测在 `theme.extract.test.ts`（41 条）：两个统计量的边界（一个黑点不该把
  「有多花」拉满）、两条映射的单调性与上下限、色调的方向、明暗倾向，
  以及「生成的皮肤真的写上了面板层与色调」。
- **真图那一半只有浏览器能量**：起 Vite + 后端 + 无头 Chrome，上传四张标定图
  （雾 / 密纹 / 黄昏 / 夜景），19 条全过。实测出来的四行：

  | 图 | 有多花 | 有多密 | 通透度 | 模糊 | 色调（亮/暗） | 明暗倾向 |
  |---|---|---|---|---|---|---|

  | 密纹（花的、无彩） | 0.66 | 0.158 | **74%** | 14px | 无 | 暗色 |

- **响应式**：断的是「**换肤没动版面**」——侧栏在每一档都还是原来的 240px、
  顶栏 56px，皮肤库在窄屏落成 1 列、768 起 3 列，10 张卡一张不少。

  但窄屏这一趟**顺手量出了一件既有的事**，记在这儿免得下次误算到换肤头上：

  | 视口 | 出厂树 `HEAD` 聊天页 | 当前树聊天页 | 当前树外观页 |
  |---|---|---|---|
  | 375 | 溢出 **65px** | 溢出 **65px** | 溢出 11px |

### 8.7 分区域：从「一根主旋钮」到「八个值，皮肤能写、用户能拨」（2026-10-03）

§8.5 把面板层做出来了，但**只有一根主旋钮**（`glass`）加一根模糊。当时那句
「用户能拨的旋钮越少越好」是对的，代价是：**「侧栏比卡片深一档」这件事只有写皮肤的人
做得到**。数据层其实早就分了区域（`sidebarGlass` / `topbarGlass` 从 §8.5 起就在），
界面上却一个都没有——换肤这件事有一半的用户价值恰恰在「拨出来」。

这一节把那一半补上：**每一项都是一条链上的一个环，而链的默认是「跟随」**。

| 区域 | 谁写在皮肤里 | 不写跟谁 | 下限 |
|---|---|---|---|
| 卡片 / 面板 | `glass` | — | 55 |
| 侧栏 | `sidebarGlass` | `chromeGlass`（不写 = 85） | 0 |
| 顶栏 | `topbarGlass` | `chromeGlass` | 0 |
| 输入框 | `fieldGlass` | `glass` | 80 |
| 浮层 | `floatGlass` | `glass` | 95 |
| 模糊 / 边框 / 浮层阴影 | `blur` / `borderAlpha` / `shadow` | 各自默认 | 0 / 55 / 0 |

#### 三件事写在一处，界面只是消费

`theme/surfaces.ts` 里多了一张**闭集**与一条**规则**：

- `SURF_KEYS`（九个）是「这一层有哪些值」的唯一定义——皮肤格式、用户覆盖的解析、
  滑块、运行时解析四处都从它派生。加一个区域只改这里一行；`theme.surfaces.test.ts`
  里那条「闭集与接口不脱节」盯着它和 `SkinSurfaces` 对不对得上——
  **漏项的症状是「皮肤里写了、用户拨不动」，而两边各自看着都对**。
- `applyOverrides(base, 覆盖表)` 是**唯一一处**把用户的值叠到皮肤之上的地方，
  运行时写 CSS 变量与预览画微缩工作台都走它。两处各写一遍的话，预览与真界面会在
  某个区域上不一致——而那种不一致正是「预览」最不该出的错。
- **拨主旋钮时，没单独拨过的区域跟着走。** 这一条不是便利，是旧行为的忠实延续：
  以前只有一根滑块，它管着卡片也管着壳；现在它仍然管着整个界面，
  只是**谁被单独拨过谁就定住**。不这么做的话，那根滑块看起来「只做了一半」。

#### 下限从「运行时的兜底」变成「滑块到不了的地方」

下限（55 / 80 / 95）原本只在 `panelAlpha()` 里兜，于是有一个说不通的界面：
**滑块能拨到 0，而屏幕上是 55%**——「我明明拨到底了，怎么还这么实」。
现在 `surfFloor()` 把地板交给控件的 `min`，`surfValue()` 交给显示的那个数，
所以**滑块的位置、显示的数、渲染出来的像素是同一个数**。

浮层那一档因此只有 95–100 五格行程。这是**有意的**：它必须压得住底下的字
（理由见 `FLOAT_FLOOR`），把地板降到 85 换来一根好用的滑块，代价是「浮层上两层字」——
而那正是这一层最先要防的事。行程短是诚实的，不是缺陷。

#### 用户覆盖从「两个标量」变成「一张表」

`ThemeConfig` 里的 `glass: number | null` / `blur: number | null` 换成
`surfaces: SurfOverrides`（一张表，拨过哪几项就记哪几项）。理由不是「表更好看」，
是**「拨过哪一项」本身是信息**——界面上每一行的 ↺ 显不显示，问的就是这张表。
写成标量的话，加一个区域要动类型、解析、存储、界面四处，而漏掉解析那一处的症状是
「拨了，刷新之后没了」。

**旧值照认**：`parseSurfaces()` 把 v2 存下来的 `glass` / `blur` 两个数折叠进这张表
（`null` = 当时那句「跟随皮肤」= 这一项没拨过）。所以升级路径上没有人会发现自己
拨过的通透度被悄悄改回皮肤那一档——这才是「带版本号」那句注释真正要防的事。
表里已经有那一项时以表为准，坏值只丢那一项（`blur: 400` 夹到 24，不是整份设置退回默认）。

#### 顺带修掉的一处「两个真值」

`ThemeProvider` 从后端回读时原来是 `setConfig(r.theme)`——**把后端那份直接塞进 state**。
平时看不出问题，但后端存的正是「上一次某个版本的前端写进去的形状」，
而这一节刚好改了形状：清过浏览器数据的人会拿到一份没有 `surfaces` 的记录。
现在那条路也过 `parseTheme`：解析这一层认得旧值、挡得住手改坏的字段，
而**外观设置不该是能把页面弄白的那一环**。

#### 验证

- **单测**：`theme.surfaces.test.ts` 21 条（闭集与接口一致、跟随规则、主旋钮与
  单拨项的优先级、坏值夹回、地板、`surfValue`）；`theme.test.ts` 34 条
  （旧标量折叠、坏值只丢一项、`glass: 0` 不被当成「没拨过」、五个区域各出一个变量、
  单拨只动一个变量）；`AppearanceSettings.test.tsx` 39 条（八根滑块都在、
  滑块下限就是地板、单拨侧栏只动侧栏那个变量、↺ 只在该行出现、
  「全部跟随皮肤」、存成新皮肤存的是生效值）。全量 **952 条 / 60 文件**。
- **浏览器**（真界面 + 无头 Chrome，出厂皮肤）：

  | 做了什么 | `--wb-sidebar-alpha` | `--wb-topbar-alpha` | `--wb-surface-alpha` | `--wb-field-alpha` | 落盘 |
  |---|---|---|---|---|---|
  | 初始 | 0.85 | 0.85 | 1 | 1 | `{}` |
  | 单拨侧栏 30% | **0.3** | 0.85 | 1 | 1 | `{sidebarGlass:30}` |
  | 刷新 | 0.3 | 0.85 | 1 | 1 | 同上 |
  | 再拖主旋钮 62% | **0.3**（定住了） | 0.62 | 0.62 | **0.8**（地板） | `{sidebarGlass:30, glass:62}` |
  | 存成新皮肤 | 0.3 | 0.62 | 0.62 | 0.8 | `{}`（覆盖让位） |
  | 刷新（用新皮肤） | 0.3 | 0.62 | 0.62 | 0.8 | 同上 |

  侧栏那一列与顶栏那一列是同一张表里的两行，而**`aside` 与 `header` 的计算样式
  真的分开了**（`rgba(255,255,255,0.3)` vs `rgba(255,255,255,0.62)`）——
  「分区域」在 DOM 上就是这件事。
- 存下来的那份皮肤里写着九个值（`sidebarGlass: 40` + 其余八项是**当时生效的那一档**），
  亮暗各自一份：`chromeGlass` 76/64 两侧不同，而用户拨过的 `sidebarGlass` 两侧都是 40
  ——覆盖是「与明暗无关」的，皮肤那一套是「每侧一份」，两者叠起来才是他看到的。

### 8.8 跨标签页同步与皮肤域验证矩阵（2026-10-01）

外观是全站设置，而工作台常开着不止一个窗口。之前在一边换肤，另一边纹丝不动，
要刷新一次才对齐。我们是 localStorage-正本架构，`storage` 事件就是为这件事生的通道：

- **只进不出**。`ThemeProvider` 监听 `storage`：`wb:theme` 变 → `setConfig(loadTheme())`；
  `wb:skins` 变 → `loadUserSkins()` + 抖 `skinsRev`；`key === null`（另一页把存储
  clear 了）→ 两边各自重读。**收到之后不回写**：传入的值本来就在 localStorage 里，
  再 `saveTheme` 一遍是空转，还会在对面那个标签页再点着一次 storage 事件——
  两页你来我往地乒乓。实现上用**对象身份**记住「这份是同步来的」（`storageApplied`），
  持久化 effect 见到就跳过；真正的用户编辑都走 `{ ...c }` 展开，一定是新对象，
  不会被误吞。
- **与持久化不打架是结构性的，不是小心的结果**：`storage` 事件只在**别的**标签页
  写入时触发，本页自己 `setItem` 不会发给自己——所以「同步进来的」与「本页改出去的」
  天然是两批，互不相认。
- 「本机是唯一真相」的原则不变：跨标签页同步的也只是正本（localStorage）自己的变化，
  后端副本仍只走「本地为空才恢复」那一条路（§8.2）。

皮肤域的承诺散在多个测试文件里，收拢成一张矩阵——**每行都指一个可执行的验证**，
量不了的（比如导入皮肤的自配色对比度）不进表：

| 承诺 | 钉在哪 |
|---|---|
| 手写三个字段就是一套完整皮肤；写错整条拒绝，不偷偷用推导值顶替 | `theme.registry.test.ts` |
| 内置 id 顶不掉；坏条目只跳过它自己；存储是垃圾时不炸 | `theme.registry.test.ts` |
| 导入是合并，校验的是合并后的结果；指名装不上的皮肤**要说出来** | `theme.registry.test.ts` |
| 带图皮肤必声明压暗与面板层；底图地址只放行站内与 http(s)；压暗有下限 | `theme.bgSkin.test.ts` |
| 对比度只对内置皮肤背书（量不了的东西不假装量过） | `theme.contrast.test.ts` |

### 8.9 流萤、氛围粒子、会动的壁纸与轮换池（2026-10-01）

来源是 dsh-theme-firefly（DSH 生态里一款「皮肤即代码」的成品角色主题）：它有
三样值得抄的东西——**好看**（深蓝黑夜空 × 萤绿）、**粒子氛围**、**壁纸管理**。
按 §8.2 的冻结原则，好看的部分全部以**数据**进来；它塞进皮肤里的功能
（音乐播放器、打字音效、按对话触发的表情包）不进皮肤——那是 app 功能不是外观，
硬塞就破了「加一套皮肤只加一份配置」。真想要，单独立项。

**1. 流萤（内置第七套）**。亮色是带一点绿意的纸底 + emerald 强调色；暗色才是
这套皮肤的本命——深蓝黑夜空（`#0a0f16`）+ 提亮过的萤绿。色阶按深海/暖调的家规
手抄一整条：亮色侧的 600 身兼「白字实底按钮」与「浅底强调文字」两职，推导推到的
那一档压不住这套皮肤自己的底色（4.21:1，`theme.contrast.test.ts` 当场抓住），
手压到 4.87 / 5.36——**「新皮肤不许进例外名单」这条纪律在它身上生效了**。

**2. 氛围粒子跟皮肤走（装饰是数据）**。manifest 新增可选 `particles`
（`sakura` / `firefly` / `none`）：缺省樱花 = 字段化之前的行为；认不出的值退缺省、
不整条拒绝（`fit` / `scrimDir` 先例）；导出时缺省的那一份不写出去（中性阶纪律）。
**款式与开关分属两个真相**：款式是皮肤的，🌸 按钮只管画不画。萤火虫画法：
缓慢上浮、横向漫游、呼吸明灭，每一只自己的大小/亮度/节奏——同起同落就成了灯串。

**3. 视频壁纸（数据不动，渲染分派）**。`bg.image` 认出 `.mp4` / `.webm` 就画
`<video muted loop playsinline>`，合法性仍由 `isSafeImageUrl` 把关——加一种
「会动的壁纸」没有给皮肤格式开第二个真相。`prefers-reduced-motion` 下不自动播：
画面在、动不在。视频进**同一个**图库（64MB 上限，与图片 20MB 分开量），后端
引用扫描与前端 keep 正则都认视频——「清理未引用」不会误删正在播的壁纸。

**4. 轮换池（时间桶，不是定时器）**。`bg.pool` + `bg.rotateMin`；
`rotatedImage()` 按 `floor(now / 间隔)` 取图。于是换图**不写盘、不需要
setInterval 撑着**——刷新、重开、第二个标签页，看的是同一块钟，自然同一张图；
**状态在时间里，不在存档里**，这正是本地优先工具该有的轮换。`effectiveBg` 把
轮换收进背景唯一的分派点（`now` 是注入参数，函数保持纯）；ThemeBackdrop 只放
一个对齐到桶边界的闹钟把自己叫醒重画。

**素材纪律（从它的 README 学的，写死成条款）**：内置皮肤的素材必须**自制或
授权明确**，仓库里不得出现来路不明的图；用户导入的皮肤是 localStorage 里的
数据，后端只有副本——**分享皮肤时，分享的是那份 JSON，不是仓库里的任何图**。
代码与素材的许可边界要在素材的出处那一页写清楚。

#### 验证

- **单测**：`theme.contrast.test.ts`（流萤两套值全过 AA，无例外）、
  `theme.registry.test.ts`（particles 解析/导出/内置快照）、
  `theme.test.ts`（轮换时间桶：同桶同图、循环取、关/空原样返回同一对象、
  池子解析去重封顶）、`ThemeBackdrop.test.tsx`（视频分派、reduced-motion
  不自动播、静态图不受影响）、`AppearanceSettings.test.tsx`（轮换 UI 三条）、
  `test_images_store.py`（视频入库去重、64MB/20MB 两道闸、视频引用受保护）。
- **浏览器**：切到流萤 → 对话页换萤火虫；上传/粘贴 mp4 → 视频壁纸带压暗；
  轮换池加两张 → 桶边界整点换图，另一窗口同一张。

## 9. 窄屏：图标轨、提示层、最低 480（2026-10-01）

**这一条是把「窄屏怎么办」这个决定写死**，免得它每次被当成一个新问题重新讨论。
起因：375px 实测横向溢出 65px——常驻 240px 侧栏吃掉 64% 宽度，输入条一排固定宽
按钮至少要 238px。选型时否掉的两个中间态：**「能打开但横向滚动」（最不该有）**与
「假装支持手机宽」（为不存在的用户优化——本仓真实的窄屏场景是桌面分屏小窗，
不是手机）。

**契约**（三档，纯 CSS，`max-[900px]:` / `max-[480px]:` 任意变体，**只藏文字不删 DOM**——
jsdom 测试照常过，`data-*` 锚点全部健在）：

| 宽度 | 形态 |
|---|---|
| ≥901px | 侧栏 `w-60` 全栏（分组、子项、最近对话、本地用户） |
| 481–900px | 侧栏收成 **52px 图标轨**：分组图标 + `title` 悬停可见，子项/最近对话/文案让位。「任何宽度都能导航」不破 |
| ≤480px | 全屏提示层（`data-narrow-hint`）：桌面排版最低支持 480px，拉宽即回来 |

**配套的下限**：输入条按钮 560px 以下收缩（46→40、发送 76→64），行宽跟着窗格走，
不再有「至少 238px」的硬下限（`App.tsx` / `CollabPanel.tsx`）。

**验收方式**：见 `docs/testing.md` §8——同一路由、逐档宽度（1440/900/600/481/480/375）、
换肤前后各量一次，出数字表；>1px 溢出即失败。新增页面或侧栏元素时，**三档都要过**。

**皮肤副本**（同日落的另一条，与契约相关的部分）：用户皮肤正本在 localStorage
（`wb:skins`），后端镜像一份（`data/skins.json`）；**本地有键就 never 用副本覆盖**——
空清单是用户删光的决定，不是丢失。皮肤中心的同步文案以此为准。

### 8.10 外观页的信息顺序：选在前、调在后（2026-10-01）

用户反馈「功能有点平铺，没有产品感」。病灶不是功能多，是**顺序与响度**：
当前皮肤 + 8 根分区域滑块压在皮肤库前面，五个同层级卡片全展开——
选择（这页九成的用途）被微调（一成的人偶尔做的事）顶到了第二屏。

重排后的顺序：**皮肤库（现画预览卡）→ 强调色 → 三个折叠区**
（微调面板层 / 自定义壁纸 / 导入导出）。两条规矩写死：

- **折叠用 `<details>`，不用 state + 卸载**。收起来的是「不吵」，不是「不在」：
  内容常在 DOM 里，测试不用先开抽屉、窄屏「藏字不藏节点」的规矩不破。
- **折叠行的右侧必须有摘要**（现在是什么模式 / 轮换几张 / 导入了几个），
  用户拨过的状态（「已自定义」徽标）要摆到收起的那一行上——
  收纳不许把「这里有你改过的东西」也一起藏了。

预览**用皮肤自己的色值现画**（`SkinPreview`，与折叠区里的大预览同一个组件），
不为每张卡备图——加皮肤时预览自动就对，这条是 §8.2「皮肤是数据」的下游义务。

### 8.11 皮肤中心：从「设置页」到「Skin Center」（2026-10-02）

用户的目标一句话：**「我在挑选和打造自己的工作台皮肤」，而不是「我在修改 CSS 配置」**。
引擎能力（§8.2–8.9）已经齐全，这一轮补的全是「把工程能力翻译成产品体验」，
一条引擎都没重写。

**信息架构（对 §8.10 的再收窄）**：当前皮肤（Hero）→ 皮肤库（主角）→ 折叠区。
三条决定写死：

- **开门第一块是「当前皮肤」**（`SkinHero`）：大预览 + 「正在使用」徽章 +
  编辑皮肤 / 恢复默认外观 + 明暗。明暗搬进 Hero——它正交于皮肤，
  描述的是「这块屏幕现在亮着还是暗着」，摆进皮肤网格会让人以为暗色也是一种皮肤。
  换肤时预览按皮肤 id 重挂 + 0.25s 淡入（复用全站 `animate-fade-in`），轻微，不做表演。
- **画廊按策展分组**（`skinGallery.ts`：推荐 / 氛围 / 极简 / 色彩 + 我的皮肤）。
  策展数据住 **UI 层**、不进 `SkinManifest`：「推荐哪几套」是产品对货架的整理，
  不是皮肤自己的属性——用户导入的皮肤没有分组，改标签也不该动数据格式。
  配套守卫测试（`skinGallery.test.ts`）：分组必须**恰好盖住**全部内置皮肤、
  一个 id 只进一个货架、标签不发给用户皮肤——「加皮肤忘了上架」当场红。
- **调参收进「高级调整」**（强调色 + 分区域 + 存成新皮肤）。「编辑皮肤」在 Hero
  上，用 ref 拨一下 `<details>.open` 把两层连起来——出口在选购区，参数在折叠区。

**预览升级为「缩小版真实工作台」**（`SkinPreview` 重画）：侧栏带选中态导航、
顶栏带搜索胶囊、两张指标卡带**皮肤自己的图表色**迷你柱状图、清单卡带状态点、
输入条、浮层。判据：看一秒就知道「套上之后我的屏幕是什么感觉」；
分区域各取各档（§8.5 的下游义务）与「读皮肤数据不读 CSS 变量」两条铁律不变。

**图片 → 皮肤改为两幕**（`SkinCreator`）：取色完成**不落地**，先给「你的新皮肤
已经生成」——整套工作台的现画预览 + 起名 + 三个出口（使用 / 存到我的皮肤 /
重新选一张）。「使用」才入库、切皮肤、背景切回跟随、该换明暗就换；
「收藏」只入库不切换。决定权在看到成品之后，这是两幕与一枪头的全部差别。

**对比度读数量真实档位**（修掉一个旧账）：以前量的是「显示用的那个色号」，
暗色下那是提亮过的 400 档——流萤暗色会显示「白字 1.5:1 低于 AA」而按钮实际
5.4:1。现在量的是**真实用法上的两对**（按钮实底 600；强调字亮 600 / 暗 400），
与 `theme.contrast.test.ts` 同一判据。附带发现：`accentPalette` 会把淡色的
600 压到 4.5 为止，所以「低于 AA」的报警路径只有手抄色阶的已知例外踩得到
（默认皮肤暗色 600），测试改用这条真实路径。

**状态色 Token（全仓颜色判据只有一条：装饰与品牌跟皮肤，状态跟语义）**：

- `--wb-accent*` —— 品牌层别名（= `--wb-violet-*` 那套强调色阶）。审计结论：
  violet/fuchsia 调色板接变量（§8 首轮）之后，**hero 渐变、stream cursor、
  `::selection`、焦点环、logo、hover/active 已经全部跟皮肤走**，组件层不存在
  「残留的旧品牌紫」——这次不再逐处改类名，只给 CSS 规则一个说得出口的名字。
- `--wb-status-success/warning/error/info/output` —— 状态层。rose/amber/
  emerald/sky/teal 那几百处工具类是功能语义（哪里坏了、哪里好了），**刻意不跟
  皮肤走**：换一套绿皮不该把「错误」也染绿。变量管的是没有类名的场合——
  `.wb-node-running` 的呼吸光晕原来手写 `rgba(14,165,233,…)`，是全仓最后一处
  「写死的品牌外颜色」，这次接到 `--wb-status-info-glow` 上。
- 侧栏 `GROUP_CHIP` 的分组色保留：那是**模块识别色**（扫一眼知道自己在哪个区），
  与状态色同类，不属于品牌。未来给皮肤定义「挂件风格」时（用户已提案），
  应该走「皮肤新增一个数据字段」的路，不走这套变量。

**挂件风格——皮肤三条腿的最后一条（同日晚些时候）**：`SkinManifest` 增加可选的
`pet: { sprite }`——**一套皮肤可以换一只「零柒」**。与 `bg.image` 同一条闸
（`isSafeImageUrl`：站内 `/skins/`、`/pet/`、`/api/images/…` 或 http(s)，
不收 `data:`——这个值会进 `<img src>`，而皮肤可能来自别人的一份 JSON）。
渲染收口在 `PetSprite` 一个组件里（挂件 / 置顶小窗 / 陪伴页 / 小屋四处共用，
`petFace` 的动作清单不抄第二份）；加载失败**逐级退回**：自定义图 → 内置动作
webp → `/pet-avatar.png`，换皮肤时 `key` 重挂、退回级数清零。不写 `pet` 就是
内置那只，一处不变。内置皮肤不带挂件资产（素材纪律 §8.9：每套皮肤配一套
九动作 webp 是资产决定，不是数据决定）——所以这条腿对**用户皮肤**完全开放，
对内置皮肤保持诚实。地址闸相应放宽了 `/pet/` 与 `/pet-avatar.png`
（同源静态文件，与 `/skins/` 同性质）。

**「我的皮肤」补全为完整的藏品操作（同日晚些时候）**：应用 / 重命名 / 删除之外，
补上两条——

- **导出单个皮肤 = 皮肤分享文件**（`buildSkinShare`）：卡片上一枚下载按钮，吐出的
  JSON **只有皮肤、没有 config**。收的人要的是「装上这张卡」，不是「连导出者的
  亮暗、强调色、壁纸一起搬过来」——`planImport` 按结构认它（没有 config 字段），
  导入时只装皮肤、外观一字不动，界面的说明也照实说「外观没动」。与「导出这份
  设置」（全量档案）是两种意图、两种形状，不共用一个文件格式。
- **编辑 = 保存修改覆盖回同一 id**：当前套着的是用户皮肤时，「高级调整」的出口
  从「存成新皮肤」变成「保存修改」——套用 → 拨旋钮 → 保存，id 不变、货架不多卡。
  内置皮肤照旧「存成新皮肤」（内置的定义在产品代码里，覆盖会在下次构建被悄悄撤销）。
  顺带修掉一笔旧账：存档从不写 `chart`，深海存的副本图表会退回出厂蓝绿——
  现在图表色跟着原皮肤走（与 `skinToManifest` 同一条规矩）。

**创建器的「用户微调」步骤**（§七流程里的第 4 步，最后一小块）：报告里那排
「从图里切出来的前几色」从展示变成**可点的强调色候选**——取色挑的那块不合口味，
点旁边任意一块就换（改的是 `manifest.accent`，色阶由推导重出；压暗与面板通透
是**按图算的**，跟着图不跟着色号走，所以不动）。候选全是这张图自己的颜色，
怎么选都不跳出这张图的气质。预览当场跟着变——微调发生在看到成品之后，
与两幕的决策权是同一条原则。

**验收**：1012 条测试（新增画廊/创建器/Hero/策展守卫/分享文件回环/保存修改/强调色微调/挂件形象 28 条）；浏览器实测——
换肤联动（流萤亮/暗：按钮、导航、logo、焦点环、读数全跟）、筛选条、
创建器全流程（页面内造图 → 取色 → 换强调色候选 → 改名 → 使用 →
自动切暗色 + 入库「我的皮肤」+ 事后说明条）走通，测试数据已清理并恢复出厂外观。
挂件换形象在真机上走通（注入 `pet.sprite` 皮肤 → 挂件与陪伴页两处精灵同步换脸，
清理后恢复内置形象）。宽度验收：IAB 视口 1280 实测 0 溢出；其余档位（901/481–900/≤480）按契约走
断点静态审计——本轮新增组件里唯一固定宽度是预览内部 ≤6px 的原语与
`max-w-[220px]` 的命名输入（flex-wrap 行内），画廊网格与全部新行均为
`flex-wrap` / 断点网格，无溢出路径。

### 8.12 设置中心：从「开发者表单」到「Settings Center」（2026-10-02）

设置模块的这次升级**不是加装饰**，是把信息架构、编辑流程与视觉语言一次理顺。
产品判据只有一条：用户能一眼看出「这里可以配什么、哪些是核心、当前是什么状态」。

**统一语言（`SettingsUI.tsx`，十一个分区共用）**：

| 件 | 管什么 |
|---|---|
| `SettingPage` | 分区页头：标题（text-lg，不画大）+ 一句说明 + 右上动作槽 |
| `SettingGroup` | 设置分组卡：组标题 + 组说明 + divide-y 行区（`divide={false}` 装资源卡/表格） |
| `SettingRow` | 一行设置：左「标题 + 说明」，右「开关 / 下拉 / 小输入」；`stacked` 竖排给长输入 |
| `SettingField` | 抽屉表单字段：label + 控件 + 提示 |
| `SettingSwitch` | 统一开关（`role="switch"`），替代设置域全部原生 checkbox（多选白名单除外——多选语义本就是 checkbox，只补 `accent-violet-600` 对齐品牌色） |
| `SettingActions` | 行尾/抽屉尾按钮区 |
| `ResCard` | 资源卡外壳：标题行（名字 + 徽标 + 状态点）+ meta + 右侧文字按钮列 |

**两条硬规矩**：
1. **页面负责浏览，抽屉负责编辑**。Provider / MCP server / 智能体 / 提示词 / 技能 /
   定时任务的编辑器全部搬进 Drawer——「列表下面永远摊着一坨表单」从此是反模式。
2. **两种保存**。偏好类（开关/下拉/数字/文本）改动防抖 800ms **自动保存**（页头
   `data-prefs-save-state` 显示状态；`prefsLoaded` ref 保证首次加载不触发回写）；
   Provider/MCP/任务等资源走抽屉里的显式「添加 / 保存修改」。测试生成先显式落盘再跑。
