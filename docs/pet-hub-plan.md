# 零柒中枢计划：让宠物成为「学 × 工作」的超级枢纽

> 目标：把零柒从**桌面挂件**变成**中枢**——它照见你在干什么、它因为你的积累而变、它能替你干活。
> 路线图分四阶段，**P1 的验收标准是「能看见」**，优化留到后面。
>
> **现状：四个阶段都做完了。** P1「看得见」§9 · P2「教它」§10 · P3「会干活」§11 · P4「收口」§13。
> 下面 §0–§8 是开工前的勘察与拍板，保留原样（包括后来被实施证明要改的几处）；实施记录在 §9–§13。

---

## 0. 一句话结论

零柒现在是**系统的嘴**（会说 13 种话），不是**你的镜子**（不反映你在干什么），也不是**你的手**（不会干活）。

把它变成中枢要补的正是这三样。而**底座已经在了**——不是从零开始，是接线。

## 1. 勘察：这个方向已经有一半的机器

在写"要做什么"之前，先摆清楚"已经有什么"。这个仓库在宠物线上投的工程量，比表面看到的多得多：

| 已有资产 | 位置 | 它意味着什么 |
|---|---|---|
| **跨模块成长聚合** | `pet.growth()` | 已经读了**学习**（`tutor_sessions`/掌握事件）、**工作**（`task_runs` + `vault` 产出）、**习惯**（`habit_logs`）、**复习**（`card_reviews`），折算 EXP + 10 级称号。**"宠物当枢纽"在数据层已经成立** |
| **能力插件运行时** | `pet_plugins.py`（openpets 七件套） | 权限 / 配额 / 存储 / 计划 / 事件 / 命令 / 面板 全部齐备，已装 `water`/`focus`/`mood`。**加一个新能力是加一条 `BUILTINS` 声明，不是改架构** |
| **13 种发言事件** | `pet.KINDS` + `emit()` | 任务跑完/挂掉、摘要、备份、订阅、到期卡、掌握、插件……**事件源已经铺满所有模块** |
| **跨模块催办** | `PetWidget.gatherNudges()` | 已经在读 tasks / tutor 卡点 / 到期卡，挑最急的一件开口，还带跳转。**"枢纽"的雏形** |
| **9 个动画状态** | `frontend/public/pet/*.webp` | `idle` `waving` `jumping` `failed` `waiting` `running` `running-right` `running-left` `review` |
| **费曼模式引擎** | `tutor.py:94` `FEYNMAN_PROMPT`、`MODES` | **"你讲给它听、它追问"的引擎已经造好了**，现在是 TutorSession 的一个 `mode` |
| **本地语音闭环** | `asr.py`（faster-whisper）/ `tts.py`（edge + SAPI） | 本地可用，不依赖云 |
| **隐私闸门** | `pet.sanitize()` | 台词一律剥掉路径与密钥。任何新能力都必须过这道闸 |
| **主动节律** | `pet.reschedule()` | 早/晚问候已挂调度器——零柒已经会"先开口" |

**结论：四个维度里，至少两个是"接线"而不是"研发"。**

## 2. 真正的四个缺口

| # | 缺口 | 证据 |
|---|---|---|
| **1** | **宠物没有"状态"** | `PetWidget.action` 只由三样东西驱动：feed 新事件（`waving`/`failed`）、聊天中（`review`）、其余 `idle`。**你是在工作还是在摸鱼，它不知道** |
| **2** | **五个动画是死资产** | 代码里 `playAction` 只传过 `waving`/`failed`/`review`，加 `idle` 共四个。**`running` `waiting` `jumping` `running-left` `running-right` 全部闲置**——你要的"工作时敲代码、学习时看书"，带宽已经发货了 |
| **3** | **宠物不会干活** | `routers/pet.py::pet_chat` 是**纯 stream，没有工具循环**。而 `core/mcp.py` 的完整工具循环早就有。零柒现在**只会说话，不会做事** |

第 3 条是最可惜的：能力在隔壁房间，门没开。

## 3. 四个维度

### 维度一（你提的）：重塑定位——从装饰到核心 Agent

**1a · 宠物即状态指示器**

零柒的形象 = **你现在在干什么**。

| 你在 | 零柒表现 |
|---|---|
| 工作（work / 引擎页） | `running` 奋力敲 |
| 学习（tutor / review） | `review` 看书 |
| 专注计时中 | `running` + 倒计时常驻 |
| 摸鱼太久 | `waiting` → `failed`，挠屏幕 |
| 刚交出一份成品 | `jumping` 欢呼 |
| 任务跑挂 | `failed` 蔫掉 |
| 深夜 | 打哈欠 / 想睡 |

**关键：这不需要模型，也不需要新数据源。** 需要的信号全都拿得到（见 §4）。

**1b · 宠物即学习陪练（费曼法）**

让零柒**本人**当那个"什么都不懂的幼崽"：你把概念讲给它听，它真诚地追问，你讲圆了它才升级。

**这一条的引擎已经存在**（`FEYNMAN_PROMPT`），缺的只有三样：
1. **一张脸**——现在它是 `/tutor` 页里一个没有形象的"学生+考官"。绑到零柒身上，`waiting` 表示没听懂、`jumping` 表示懂了。
2. **专属成长**——现在一场教学固定 `EXP_SESSION = 5`。**"把零柒教会"应该是最重的一档 EXP**，因为费曼法是这套系统里最强的学习动作。
3. **语音闭环**——`asr` + `tts` 都在本地，"你对着零柒讲解"是可达的（放 P3）。

---

### 维度二（我补）：宠物即入口——从"会说话"到"会干活"

零柒的聊天现在**没有任何工具**。你说"开始 25 分钟专注"，它只会**回你一句像样的废话**。

接上 `core/mcp.py` 的工具循环之后：

| 你说 | 现在 | 接上工具后 |
|---|---|---|
| 开始 25 分钟专注 | "好的，加油！" | 真调 `focus/start`，面板倒计时跟着走 |
| 清一个卡点 | "建议你去学页看看" | 真查 `tutor_stuck`，列出那几条 |
| 我今天学了啥 | 编一段 | 真查 `mastery_events` + `card_reviews` |
| 把这份研究存进 notes | 不会 | 真写 vault（走 `sanitize` + 产出回执） |

这是**把"Agent 工作流"这条趋势落到零柒身上**，而且复用现成的工具循环，不是新造。

**同时它是最高杠杆的一条**：一旦零柒能干活，"宠物"和"工作台"就不再是两个东西——宠物是工作台的**对话式门面**。

---

### 维度三（我补）：宠物即节律——负面状态与后果

你要的"疲劳值 / 抑郁 / 强制休息提醒 / UI 变灰"，本质是**情感绑定**。

它的成立条件**不是宠物会说什么，而是系统真的改变行为**。嘴上说"该休息了"没有用；页面降饱和、定时任务停止打扰、休息卡真的挡住，才有用。

**状态 → 后果** 的几条（P1 只做第一条）：

| 状态 | 触发 | 后果 |
|---|---|---|
| 摸鱼太久 | 无输入 > N 分钟 | 宠物挠屏幕 + **页面降饱和（变灰）** |
| 连续工作太久 | 有活动且 ≥ M 小时无休息 | 零柒进入 `failed` + **强制休息卡**（可关闭） |
| 深夜 | 23:00 后仍在活动 | 只提醒一次，不重复 |
| 专注完成 | `focus` 到点 | `jumping` + 记一笔"今天专注 N 次" |

> ⚠️ **这里与现有代码库的一条硬立场冲突，见 §5。这条必须你拍板。**

---

### 维度四（我补）：宠物即收口——积累要有形状

13 种事件现在只是一列气泡。让它们变成**零柒身上的东西**：

- **小屋 / 桌面**：它攒下的产出、徽章、习惯道具摆出来——"我攒了什么"一眼看得见
- **成长史时间线**：不是聊天流，是**里程碑**（第一次说通一个概念、第一次连跑七天、交出去第 10 份）
- **每个模块一个"投喂"动作**：产出成品 → 零柒叼回来；清掉卡点 → 它长一岁；任务连续跑成 → 它换毛

这条是四个维度里**最"产品"**的一条，也是最晚该做的——因为它的素材来自前三条。

## 4. 主线：零柒的状态机

四个维度共用一个东西：**一个诚实的、从真实数据算出来的状态**。这跟 `pet.status()` 和 `pet.growth()` 是同一条家规——**算出来的，不是编的**。

### 输入信号（全部现成）

| 信号 | 来源 | 现成? |
|---|---|---|
| 你在哪个模块 | 前端 `location.pathname` | ✅ |
| 是否在专注计时 | `pet_plugins.focus_remaining()` | ✅ |
| 今天学到什么程度 | `tutor_sessions` / `mastery_events()` | ✅ |
| 今天卡了什么 | `tutor.stuck_points()` | ✅ |
| 今天产出多少 | `vault/{research,decisions,conflicts,recap,deliver}` mtime | ✅（`pet._count_outputs()` 同款） |
| 今天跑了多少任务 | `task_runs` today | ✅（`pet.status()` 已有） |
| 今天聊了多少 | `messages` today | ✅（`pet.status()` 已有） |
| 心情 | `pet_plugins.mood` | ✅ |
| 此刻几点 | `datetime.now()` | ✅ |
| 距上次活动多久 | `messages.created_at` max | ⚠️ 需加一个查询 |
| 键鼠活动 | 前端 `mousemove`/`keydown`/`visibilitychange` | ⚠️ 需加，**纯前端，不上报** |

### 输出

```
{
  "mode": "focusing" | "working" | "learning" | "reviewing" | "idling" | "tired" | "sleepy" | "celebrating",
  "action": "running",          // 直接对应 /pet/*.webp
  "energy": 0..100,
  "line": "…",                  // 可选的一句台词
  "since": "2026-09-14T10:00:00"
}
```

**纯函数优先**：`(信号, 现在) -> 状态` 不碰 DB、不碰网络，照 `pet_plugins` 里 `roll_day` / `water_due` / `focus_due` 的先例。这样规则可以被单元测试完整覆盖，不需要起服务。

## 5. 需要你拍板的三件事

### ① 精力值的口径 —— 这条与现有代码的价值观直接冲突

现有代码库有一条**很硬、写了三遍注释**的立场：

> "只增不减 —— 每一项都是累计计数，没有任何一处会因为『今天没做』而回落。没有扣分、没有掉级、没有还欠。"
> —— `pet.py:275-284`

而"疲劳值 / 抑郁"天然是**会回的、会有负面的**。两者不能同时无冲突地存在。

我的建议（**待你确认**）：

> **负面状态只描述"此刻"，不记账、不掉级。**
> - **等级与 EXP 永不回落**（沿用现有立场）
> - 精力是**当下的实时量**，跨天清零、不进历史、不显示"你还欠 N"
> - 零柒的状态是"**我现在有点累**"，不是"**你欠了 3 小时专注**"

这样既拿到情感绑定的效果，又不破坏"永不欠债"的家规。

**如果你要的是真正的记账式疲劳（连续 N 天熬夜就掉状态），那是另一种产品哲学，我需要你明说。**

### ② 变灰的强度

- (a) 只让**宠物区域**降饱和（最轻，无侵入）
- (b) 让**当前页**降饱和（有存在感，可能烦）
- (c) **整站**主题变暗灰（你要的原文，最强，但会激怒人）

我倾向 (a) 起步、留 (b) 的开关。**需要一个"我就是要工作别管我"的关闭路径**——否则它从陪伴变成管教。

### ③ 摸鱼检测的边界

键鼠活动是**最敏感的数据**。我建议：**纯前端推断、不落库、不上报、不发网络请求**。后端只知道"宠物现在该显示无聊"，不知道你在不在电脑前。这符合 `pet.sanitize()` 那条隐私闸门的精神。

**这条我要你确认，因为它决定了架构。**

## 8. 风险

| 风险 | 缓解 |
|---|---|
| **变灰激怒用户**（"我请你陪我，不是请你管我"） | 必须有一键关闭；默认弱（只宠物区）；只在明确长时间无活动时触发 |
| **状态误判**（刚离开座位 3 分钟就"你摸鱼了"） | 阈值放宽、状态有迟滞（hysteresis）、不弹通知只改形象 |
| **纯前端推断失准**（切到别的窗口干正事） | 用 `visibilitychange` 而非只看键鼠；宁可不动也不误判 |
| **零柒变成话痨** | 沿用现有"克制"立场：`emit` 已有配额 + 每日一次 + 30 分钟静默 |
| **疲劳机制与"永不欠债"家规冲突** | §5① 必须拍板后才动 P1 的精力条 |
| **P3 工具循环带来副作用**（宠物误写 vault） | 工具白名单 + 写操作走产出回执 + 复用 `sanitize` 闸门 |

### 实施中发现并修掉的三个真问题

1. **`tired` 是一个永远命中不了的模式。** `FATIGUE_CAP` 早先设成 55，白天最多扣到
   `100-55=45`，跌不破 `LOW_ENERGY=40`；而夜里又先被 `sleepy` 截走。封顶必须低于
   `100 - LOW_ENERGY`，现在改成 65（→ 白天最低 35），`test_tired_is_reachable` 锁住这个下界。
2. **单位错，所有疲劳被除了 60。** `active_span_min` / `fresh_output_min` 本来就是
   **分钟**，却走了"秒 → 分钟"的换算：600 分钟的一天被算成 10 分钟。拆成
   `_mins_from_sec`（秒）与 `_mins`（分钟）两个函数，并补了边界测试。
3. **`last_activity_sec` 差一个时区。** 库里是 naive **UTC**（`models.utcnow()`），
   而 `now` 是本地朴素时间；直接相减在 UTC+8 下凭空多 8 小时——你刚说一句话，零柒却
   以为你走了半天。改成两头都在 UTC 里比。

### 顺带发现、并已修掉的既有问题：`pet.status()` 的时区错位

`pet.status()` 用**本地日期** `LIKE '<日期>%'` 去比 **UTC** 的 `created_at`。方向是
**双向错**的：既漏掉本地 00:00–08:00，又把第二天 00:00–08:00 算进今天。

它只影响 `pet.greeting()` 那句「系统侧：今日任务完成 N 失败 M」——`/api/pet/status`
在前端没有任何消费方（全仓库 grep 过），所以症状是**零柒问候时报错一天的数字**。

修法：换算收口成 `pet.local_day_utc_bounds()`（**唯一出处**，`pet_state` 改为复用它，
不再各写一份），两条查询从 `LIKE` 改成 `>= ? AND < ?` 的 UTC 区间。

**A/B 实测**（本机偏移正好 +8:00）：

| 库里只有一行 | 旧口径 | 新口径 |
|---|---|---|
| 本地**今天** 03:00（存成 `09-14 19:00` UTC） | `tasks_done=0` `tokens=0` ❌ 整行漏掉 | `tasks_done=1` `tokens=18` ✅ |
| 本地**明天** 03:00（存成 `09-15 19:00` UTC） | `tasks_done=1` `tokens=18` ❌ 张冠李戴 | `tasks_done=0` `tokens=0` ✅ |

回归测试：`test_status_counts_a_run_from_early_local_morning`、
`test_status_ignores_early_local_morning_tomorrow`、
`test_status_counts_tokens_from_early_local_morning`，外加把语义钉死在显式时区上的
`test_local_day_utc_bounds_pins_a_known_offset`（**与机器时区无关**，因为偏移是传进去的）。

> 诚实边界：偏移为 0 的机器上（CI 是 UTC）两种写法等价，所以前两条在那里不构成鉴别。
> 它们真正的价值在带偏移的开发机上——而带偏移的机器才是这个 bug 的现场。

### 最关键的发现：验收要的那件事**不在 `mcp.py` 里**

「开始 25 分钟专注」属于 `pet_plugins`（插件运行时），不是 `mcp` 的内置工具。
所以 P3 的正身不是"把 `mcp` 的工具接给宠物"，而是**把插件能力声明成工具**。

做法：插件自己声明「模型可以怎么调我」——`BUILTINS[*]["tools"]`。这与 openpets 范式
一致（能力由插件声明，运行时统一提供），而且**工具名与参数形状是代码的事**，所以
从代码声明现算，而不是读库里那份安装时的 `spec_json` 快照（真读那个，线上已装好的
三个插件一个工具都长不出来）。

### 「同一条路」是这一条的全部承诺

`pet_plugins.call_tool()` 直接调 `command()`——就是面板按钮走的那一个函数。配额、
隐私闸门、面板刷新、一次性作业重排全都只走一遍。

> **模型能做的和你在面板里点一下能做的完全等价。** 有两套语义迟早会分叉。

### 白名单：默认保守

`prefs.pet_tools`（逗号串或数组；**空串 = 一个都不给**，必须能和"没配"区分开）。

默认给：`pet_focus_start/stop`、`pet_water_drink`、`pet_mood_set`、`memory_save`、
`memory_list`、`kb_search`。

默认**不给**：`vault_write_file`、`memory_delete`、`image_gen`、`web_search`、
`fetch_url`、MCP 外部工具。理由：这是角落里的一个陪伴面板，不该让它悄悄改你的笔记，
也不该让一次图片生成把对话卡住一分钟。

内置工具不走插件运行时，所以**两处都过白名单**——只过滤一边，白名单就是摆设。

### 新增一条**登记在册**的提示词，而不是夹带

`_PET_TOOL_RULE` 放在 `routers/pet.py`，并在 `prompts._SPECS` 里登记（`count` 31 → 32）。
**没有**偷偷拼进 `pet.CHAT_SYSTEM`——那会改掉一条已注册提示词的指纹，等于绕过登记中心。
这与 `chat.py` 的 `_OUTPUT_RULE` 是同一个做法。

它的四条要求都对着一个具体的翻车方式：不说「你有工具」→ 退化成纯聊天；不说「别替
用户决定」→ 它会积极过头地替你开计时器；不说「别复述工具输出」→ 它把事实原样念一遍；
不说「报错照实说」→ 工具挂了它假装成功。**第 2 条在验收里单独测了。**

### 语音的验收：用应用自己的 TTS 喂假麦克风

headless 里没有麦克风，但 Chromium 可以拿一个 **WAV 文件**当麦克风输入
（`--use-fake-device-for-media-stream` + `--use-file-for-fake-audio-capture`）。
而那个 WAV 是**应用自己的 TTS** 合成的（`/api/tts` + SAPI → 正好是它要的 PCM WAV）。

于是这是一个**完整闭环**：

```
应用 TTS 说「开始25分钟专注」→ 当成麦克风输入 → MediaRecorder 录下来
→ /api/asr/transcribe → 本地 whisper → 零柒收到（说完直接发）
→ 它回答 → 朗读把它念出来
```

实测（**`problems=0`**）：

| 环节 | 结果 |
|---|---|
| 录音 | `created:1 started:1 stopped:1 sizes:[39383]` |
| 转写 | `"開始25分鐘專注"`（status 200，**一字不差**） |
| 发出 | 用户气泡就是这句——「说完直接发」成立 |
| 它做事 | 回执 `⏱ 专注 25 分`；后端 `{"running":true,"remaining":1496}`；面板 `剩余 25 分 / 停` |
| 它回答 | 「25 分钟专注开始，到点提醒你。」 |
| 朗读 | `/api/tts` 请求数 = **1** |

证据：`.tmp-pet/verify_voice.mjs` + `shot-voice.png` + `verify-voice.json`。

> **这一条验收的过程本身值得记一笔**：它连续三次「失败」，三次都是**我的脚本**在骗我——
> 先是在模型回完之前取样（读到的是「正在想」的占位符 ▊），然后是「气泡里有字」这个判据
> 被工具回执满足（正文还没来），最后是没等本地 whisper 加载完模型就往下走。
> 产品一次都没错。**端到端验证的价值就在这里：它会把「你以为它在做的事」和
> 「它真的在做的事」分开——但前提是你别把脚本的错当成产品的错，也别反过来。**

## 12. 一句话总结

**这个方向已经有一半的机器**：成长聚合、插件运行时、13 种事件、9 个动画、费曼引擎、本地语音——都在仓库里。

缺的是把零柒**接上去**：给它一个状态（维度一）、给它后果（维度三）、给它手（维度二）、给它积累的形状（维度四）。四个阶段现在都做完了，见 §9–§13。

一条贯穿全程的家规值得单独说：**凡是能从真值算出来的，就不要再存一份。** 状态是算的
（§9）、「教它」是算的（§10）、屋子里每件东西也是算的（§13）——所以产出文件一落盘，
它身上就多一件东西，**没有任何一处「发奖」的代码要记得被调用**。

## 13. 实施记录 · P4（已完成）

### 这一条最要紧的拍板：**东西是算出来的，不是发的奖**

小屋没有物品表、没有「发奖」写库、没有 hook 要挂到五个模块里去。屋里每一件东西都是
某个真实累计量跨过某个门槛的结果（`core/pet_room.py` 里那张 `LADDERS` 表）：

| 线 | 第一档（徽章） | 往上的摆设 |
|---|---|---|
| 交出去的成品 | 📄 第一份成品 (1) | 📦 一摞成果 (5) · 🗄 成果柜 (25) · 🏛 成品库 (100) |
| 搞懂的概念 | 📖 第一个搞懂的概念 (1) | 📚 一排书 (5) · 🗃 一整架书 (25) |
| 讲给零柒听 | 🎓 第一次把它讲通 (1) | 🧑‍🏫 一块小黑板 (5) · 🏫 一间小教室 (20) |
| 跑成的工作流 | ⚙️ 第一次跑成 (1) | 🛠 一张工具台 (10) · 🏭 一间车间 (50) |
| 复习 | 🃏 第一张卡 (1) | 🗂 一个卡片盒 (50) · 🗄 一个卡片柜 (500) |
| 打卡 | 👣 第一天打卡 (1) | 🔥 一周的火 (7) · 🌿 长出一棵小植物 (30) · 🌳 一棵树 (100) |
| 专注 | 💡 第一次专注 (1) | 🕯 一盏台灯 (10) · 🪑 一把好椅子 (50) |

好处不是省事，是**不可能不同步**：产出文件一落盘，屋里就多一件；删掉历史，它才少一件。
P2 那句话在这里第二次成立——**宠物不需要被通知，它读同一份真值**。

**代价写清楚**：一件东西的日期 = **跨过那个门槛的那一刻**（第 5 份成品落盘的时间），
而那是从今天的历史里算出来的——所以**删掉旧文件会让日期漂**。这是「算出来」的固有
代价，换来的是「永不欠账、永不失同步」。

### 第二件拍板：`carried`（它叼回来那件）**不是**门槛那件

门槛是稀疏的（第 1、5、25、100 份），可「交出一份成品 → 零柒叼回来」**每一份都发生**。
第一版只报「屋里最新到手的一件」，于是交出第 4 份时，它身上什么都不变——**验收那句
话会假装成立、实际是空的**。

所以身上挂的是 `carried`：门槛那件与架上最新那份，**谁新算谁**。这一条是被验收逼出来的，
不是设计出来的（见下面的「发现的问题」第 1 条）。

### 第三件拍板：「投喂」是自动的，**不做喂食按钮**

原文写的是「每个模块一个投喂动作」，落地的样子是：**你在那个模块做完的每一件事，就是
一顿饭**（`today.meals`）——交出成品 / 跑成工作流 / 说通概念 / 讲给它听 / 打卡 / 过卡 /
专注。没有「喂它」按钮，理由两条：

1. **手动喂食没有真值可喂**。一个按钮能喂的东西，要么是假的仪表，要么是把你已经做过的
   事再点一遍——那是同一件事存两份。
2. **会饿的宠物 = 一笔债**。这个仓库的家规是「只增不减、没有还欠」，而「它饿了」正是
   最典型的欠债口吻。所以：**零柒不饿**。今天没吃东西时，界面说的是「它不饿，今天还没
   吃的。等你做完点什么，它就有得吃了」——事实，不是账单。

反转路径：真要一个手动投喂动作，它应该是**拿一份真产出喂它**（消耗真东西），而不是点
一下加一颗心。

### 时间：三种口径，一次说清（这一层唯一复杂的部分）

这个仓库有三套时间，`pet_room` 全部先归一成 aware datetime，再输出**两个字段**：

| 来源 | 库里是什么 | 怎么读 |
|---|---|---|
| `task_runs` / `tutor_sessions` / `card_reviews` | **naive UTC**（`models.utcnow()`，SQLite 丢了时区） | 当 UTC 补上 |
| `pet_events.created_at` | **本地 aware** ISO | 解析出什么就是什么 |
| `habit_logs.day` | **本地日历日** 字符串 | 本地零点 |
| vault 文件 mtime | **本地 epoch** | 直接 `fromtimestamp` |

给前端的是 `at`（本地墙钟串，给人看）+ `at_ts`（epoch，排序与「多久以前」）。
**前端因此不必猜时区**——它要是拿 `new Date('2026-09-14T02:00:00')` 去算，在别的机器上
就是另一个结果。测试把这些钉在**显式时区**上，与跑测试的机器在哪无关。

### 实施中发现并修掉的三个真问题

**一、架子与账本用了两个「成品」的定义（浏览器验收抓出来的）。**
第一趟验收里，小屋的架子上赫然挂着一份 `tasks/RAG一句话-….md`——那是定时任务的落盘产物。
原因是架子直接用了工作页那张清单（`work.list_outputs`），而它比 `pet._OUTPUT_DIRS` 宽：
连 `tasks/` 的工作流产物、`notes/` 的成文都算。于是会出现**「架上 4 份、成长说交出 2 份」**
这种自己打自己脸的说法。
修法：把「成品」的定义收成 `pet.is_output_path()` **一处**，小屋的架子、屋里的东西、
今天的投喂、成长值全用它。工作页那张清单保持宽——它答的是另一个问题（「系统生成了哪些
文件」）。**两个口径不必相同，但同一句话里只能有一个。**

**二、插件事件分不出是谁发的。**
`_emit_for()` 三条线（喝水 / 专注 / 心情）都发 `kind="plugin"`，**不带插件名**。于是
「专注过几次」这件事在库里根本没有形状——要么不做这盏台灯，要么去台词里找「专注」两个字
猜。猜文本正是这个仓库反复拒绝的做法。修法是一行：`pet.emit("plugin", …, detail=name)`。
诚实的边界：**只有改过之后才开始记**，之前的历史不追认（没有就是没有）。

**三、`pytest` 的 `tmp_path` 在本机沙箱里用不了。**
系统 temp 被拒（`PermissionError: …Temp\pytest-of-TX`），而 `conftest.py` 早就为此把
可写路径都挪进了项目内 scratch。新测试一开始用了 `tmp_path`，报的却是 pytest 插件内部的
错——**看起来像环境坏了，其实是测试写错了地方**。改用项目内 scratch。

### 我自己的操作事故：一次把四个测试文件写坏了

这一轮最大的代价不是功能，是我**又犯了一遍自己写下的错**。为了把
`latest: → carried:` 这个纯 ASCII 的重命名批量做掉，我用 PowerShell 读了源文件再写回：

```powershell
$t = (Get-Content $p -Raw) -replace 'latest:', 'carried:'
[System.IO.File]::WriteAllText($p, $t, ...)
```

`Get-Content` 在 Windows PowerShell 里按**系统 ANSI（cp936）**解码无 BOM 的 UTF-8 文件，
中文立刻变成乱码；再按 UTF-8 写回，文件就被**永久**破坏了。不是「字符变难看」那么轻：
UTF-8 的字节被 GBK 成对解释后**字节对齐会错位**，解码器对不上的地方吐 `?`，
**连换行都会被吞掉**——四个测试文件（`PetWidget` / `CompanionPage` / `GrowthPage` /
`RoomPane`）当场变成语法都不合法的文件。

恢复过程（记下来，因为下次还会有人这么干）：
1. 用**同一个 .NET 编解码器**做逆运算（`GetEncoding(936).GetBytes` → UTF-8 解码），
   把能救的救回来：598 行里 94 行有损、149 个不可逆的点。**逆不回去**——对齐错位之后
   那段信息已经没了。
2. 三个文件我有完整的原文（本会话读过 / 自己写的），**直接重建**；`PetWidget.test.tsx`
   有 600 行、只读过片段，于是**以损坏文件的 ASCII 骨架为规格重写**（中文从被验证的
   组件与断言里取回来）。
3. 重建后靠 `tsc` + vitest 当**判据**：用例数一个不少（30 / 12 / 9 / 9），全绿。

教训要写成能执行的，不是「小心点」：

> **改文件只用 read / edit / write 工具。shell 里不要对任何可能含非 ASCII 的文件做
> 读-改-写**——哪怕你要改的只是一个 ASCII 标识符。`-replace`、`Set-Content`、
> `WriteAllText` 全是雷；`Get-Content -Encoding utf8` 也救不了你忘了写它的那一天。

（我上一轮就写过「带非 ASCII 的源文件不要用 shell 文本替换」，这一轮照样踩——所以这次
把**机制**写下来了：不是手滑，是 `Get-Content` 的默认编码。）
