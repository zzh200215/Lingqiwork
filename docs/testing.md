## 1. 用哪条命令（按目的选，别再每次跑 13 分钟）

| 目的 | 命令 | 实测耗时 |
|---|---|---|
| **改一处、想看结果** | `.\.venv\Scripts\python.exe -m pytest tests/test_<受影响的那个>.py -q --no-header -p no:cacheprovider` | **7–30 秒** |
| **收工前验一轮**（推荐） | `.\.venv\Scripts\python.exe run_tests_fast.py`（可 `WB_TEST_WORKERS=8` 调并发，默认 6） | **3.8 分钟** |
| 原版串行（CI 用） | `.\.venv\Scripts\python.exe run_tests_fast.py test_tutor` 或 `uv run python run_tests.py` | 13 分钟 |

`run_tests_fast.py` 就是 `run_tests.py` 的并行版：**同样的「一文件一进程」隔离**，
只是同时跑 6 个。本机 `uv` 的缓存目录写不进去（`Failed to initialize cache`），
所以一律用 `.venv\Scripts\python.exe`。

**别做的事**：不要为了快把全量塞进一个进程——实测那样会有 **9 个假失败**
（`test_research.py` 被前一个模块留下的状态带塌），看着像回归、其实是串味。
也不要在开发途中反复跑全量：改完再跑一次就够。

> **实测补充（2026-09-20）**：`run_tests.py`（串行原版）在这台机器上要 **22–27 分钟**，
> 比上表的 13 分钟更慢。这一轮因为**没先读这一页**，连着跑了 4 次，其中两次还是开发
> 中间态（等于白跑），一个多小时没了。收工前用 `run_tests_fast.py`；中途只看受影响的那
> 一个文件。**看全量结果仍然不要截断**（§4 那条已经因为截断丢过一次线索）。

## 2. 坑一：`conftest` 的临时目录（沙箱专属）

`tests/conftest.py::_SANDBOX` 用 `tempfile.mkdtemp()` 建随机名目录。在文件沙箱下，
**子进程不能在那种随机名目录里再建子目录**（`os.mkdir` → `WinError 5`），于是
`app/config.py` 的 `DATA_DIR.mkdir` 当场挂在 import 阶段。

`run_tests_fast.py` 已经处理了（每个子进程一个固定基目录的 TEMP）。
手工跑单文件时如果撞上，把 `TEMP`/`TMP` 指到项目内一个已存在的目录即可。
**这一条只影响「怎么跑」，与测试本身无关** —— CI 与不带沙箱的本机用原版即可。

> **2026-09-20 又栽一次（记在这里，防第三次）**：没先读这一页，于是从零把这条又推了一遍
> ——用 `mkdtemp` / `mkdir(0o700)` 反复试探，得出结论「这台机器跑不了 pytest」，
> 还去申请了 `danger-full-access`。**正确动作这一页第一行就写着**：用
> `run_tests_fast.py`，或手工跑时把 `TEMP`/`TMP` 指向项目内已存在的目录。
>
> **一条待验的猜测**（没验证，别当结论）：同一天 `reindex_all()` 撞的
> `chromadb … Failed to apply logs to the metadata segment`、以及随后整个 collection
> 读不出来（`count()` 都失败），**可能同源**——chroma 的 compactor 要建新的 segment 目录，
> 受限令牌下建不进去。当时同样没设 `TEMP` 就下结论「索引坏了」，最后靠全量重建绕过。
> 政策已改成 `danger-full-access`，所以**在受限模式下复现不了**；谁再遇到，
> 先设 `TEMP` 试一次再决定要不要重建——重建一次是 75 秒和一次全量重嵌。
>
> **教训一句话**：`docs/` 这一页是「别再从零推一遍」的，不是事后读物——**动手前先读 §1–§3**。

## 3. 坑二：内联脚本里的中文（这条最贵）

**不要**用 `pwsh -Command "... here-string ..."` 写带中文的 Python 探针。Windows 会把内联
脚本文本按本地代码页（cp936）解释，**中文进到 Python 里就已经是乱码**，于是：

- 探针查一条确实存在的中文行 → 报「查不到」；
- 你以为是产品 bug，换一种查法再试 → 还是查不到（因为参数本身就是错的）；
- 反复几轮，代码一个字没改，时间没了。

**规矩**：探针/临时脚本**一律用 `write` 工具写成 `.py` 文件（UTF-8）再执行**，绝不内联。
与 `pet-hub-plan` §13 那条事故同源（`Get-Content` 读改写毁文件）——差别只是这次毁的是
「我看到的东西」，不是「盘上的东西」，所以更隐蔽：**乱码看起来像一个 bug。**

## 4. 判读输出的两个注意点

- **测试模块之间共享状态**：`conftest` 只在**每个模块开始时**清沙箱，模块内跨用例的状态要
  各自收（`test_tutor._reset()` / `test_agent_orchestration._clear()` 都得管住自己新写的表）。
  新加一张会被写的表，就要同时想清楚谁负责收——这一轮为它栽过两次。
- **磁盘上的临时目录也跨用例可见**（2026-09-17 修）：`test_agent_orchestration` 里两条用例都往
  `meetings/<日期>-周会/` 写文件，而文件名带**分钟**（`_write_vault` 的 `%Y-%m-%d-%H%M`）——
  同分钟时后者覆盖前者、跨分钟时俩都在，于是「文件夹里正好三个文件」那条断言在全量里挂了一次
  （`assert 4 == 3`；单跑永远同分钟，所以查不出来）。**别对着磁盘数总数**：数「该在的那几个在不在」。
- **`test_tts.py` 在并发全量下偶发失败**（本机 4 次全量里挂过 2 次）：涉及音频设备/时序，
  单独跑 5 次全绿。**先单独复跑再当回归**，别浪费一轮排查。
- **前端也有墙钟依赖：「写死的夹具日期 + 相对时间渲染」的组合**（2026-09-22 撞到）：
  `RoomPane.test.tsx` 的夹具里是 ISO 字面量（`at: '2026-09-15T10:00:00'`），而技能卡渲染的是
  `ago(…)`（「7 天前」），断言却写着「**整屏**不该出现『7 天前』」——日历一走过第 7 天它自己就红，

### 失败详情现在留在输出里（2026-09-16 起）

`run_tests_fast.py` 原来只打印每个文件失败后的**最后一行**（`1 failed, 10 passed`），
于是「哪条断言炸的」永远丢了——上面那条 `test_report_stream` 就是这么变成一笔糊涂账的：
知道文件名，不知道断言。现在失败的那一份会把**尾巴 40 行**一起带出来（复现命令、断言行、
异常类型都在里面），并且父进程与子进程**统一按 UTF-8 输出**——不然 GBK 控制台会把
中文断言消息编成乱码，甚至用 `UnicodeEncodeError` 把 runner 自己干掉（真撞过）。

**为什么是 40 行而不是 20 行**（2026-09-17，见上面那条 `test_pet_tools`）：**收集阶段**的错误，
关键帧在栈的**上层**（谁 stat 的它），而最后 20 行只留得下栈底那一帧（`pathlib … in lstat`）
——那条线索就这么废了。断言错误的关键帧在最下面、收集错误的关键帧在最上面，所以两头都得留宽。

## 5. 要真跑起来的那几种：先跑 `--dry`

有三类东西**跑一次要真调模型**（第四类只借本地 embedder），它们的开关与纪律各不一样
（都不在 `pytest` 里）：

| 要测什么 | 命令 | 成本 |
|---|---|---|
| 四个引擎的 golden set | `.\.venv\Scripts\python.exe smoke_engine_eval.py [引擎] [--no-judge]` | 每引擎十几条调用 |
| 一份技能包有没有用 | 界面上的「量一遍」（`core/skill_eval.py`） | 每条用例问两次 |
| **重讲判分准不准**（PLAN2 P2-1） | `.\.venv\Scripts\python.exe smoke_judge_eval.py [--dry] [--model X] [--no-save]` | 36 条 = 36 次调用 |
| **话题↔概念的语义阈值**（PLAN2 P2-2） | `.\.venv\Scripts\python.exe smoke_cross.py` | 免费，但要本地 embedder（首次加载 6-7 秒） |
| **话题↔技能的匹配阈值**（PLAN3 S1） | `.\.venv\Scripts\python.exe smoke_skill_match.py` | 免费，但要本地 embedder（首次加载 6-7 秒） |

## 6. 并发 / 长跑量法的三个新坑（2026-09-20）

> 起因：给 RAG 加「超窗块窗口化编码」之后，用 `smoke_strategy.py`（3 路并发、每条走
> `asyncio.to_thread`）量分档，撞出 `RuntimeError: Already borrowed`。三个坑都不在
> pytest 里，所以记在这儿。

### 6.1 并发编码会撞 `Already borrowed`（真崩，已修）

HF 的 fast tokenizer **每次调用都会改写自己的截断/补齐配置**
（`transformers` 的 `set_truncation_and_padding` → `self._tokenizer.enable_truncation()`），
而那是**同一个 Rust 对象**。两种调用形态交错就撞：

```
_windows 里的 tk(text, truncation=True, max_length=…)  → _encode_plus（设截断）
model.encode(texts)                                    → _batch_encode_plus（设补齐）
```

实测**单独跑任一种都干净**，混着跑（也就是 `embed_one`，每个查询都要走）3 线程就必现。
而并发检索是这个应用的常态（评测器 `gather`、引擎并行取材），所以 `embedder.embed` 里把
「分词 + 编码」串在 `_encode_lock` 下。**修复后逐位复现 P1a 的全部数字**（0.6176 / 0.8235 /
0.8824 / 0.7206，注入 2549 全同），确认是纯正确性修复、没改语义。
回归测试：`tests/test_embedder_threadsafe.py`（本地有模型缓存才跑，CI 保持离线）。

**判据**：并发量法里出现检索失败，先怀疑这里，别先怀疑检索质量。

### 6.2 检索失败会被算成 miss（量表会**悄悄**变差）

`evals._one_case` 把检索异常写进 `out["error"]`、`rank` 留空——**失败的用例按 miss 计**。
所以「指标掉了」可能是「并发崩了一半」，而不是「检索变差了」。量之前先查一遍
`EvalRun.detail_json` 里 `error` 非空的条数（**写 `.py` 探针去查，别内联**，见 §3）。

实测（2026-09-20）：查全部 30 条运行，**0 条带错误**——所以 RAG升级.md §3 里那批基线 /
压块 / 池化数字没被污染。但那是运气好，不是设计：以后并发路径出的静默失败会直接伪装成
「检索变差」。**要么先查这一遍，要么就该让 `_one_case` 把 error 单独计数、不进分母。**

### 6.3 长跑脚本的 stdout 要**行缓冲**，而且别只看退出码

`sys.stdout.reconfigure(encoding="utf-8")` 不够：管道下 stdout 是**块缓冲**，而真模型脚本
在解释器退出阶段可能因为流式响应收尾报错（实测 `httpcore` 的 async generator：
`generator didn't stop after athrow()`）——**进程带着没刷出的缓冲死掉 → 输出全空、退出码 1**。
本轮撞过一次：整轮 6 分钟的量法跑完了，报告一个字都没留下，看起来像脚本根本没跑。

→ `sys.stdout.reconfigure(encoding="utf-8", line_buffering=True)`。
→ 并且**别只看退出码**：这些脚本的 1 常常来自收尾噪音（`smoke_cross.py` 的 1 本来就是
正常的，见 §5）；判成功的依据是它末尾那行结论有没有打出来。

> **2026-09-20 又栽一次**（Agent A0）：`smoke_agent.py` 第一版**没加** `line_buffering=True`，
> 于是付费跑分开始后 6 分钟里一个任务行都没刷出来 —— 只能靠进程 CPU 与到 provider 的 TCP
> 连接**猜**它还在跑。补上之后立刻看得见逐条进度。**这条规矩在本页 §5 与
> `docs/r-checklist.md` §1 第 8 条里都写着**，不是不知道，是没照做；所以本页现在把清单
> 提到了最前面（§0），以后开工先扫那几行。

### 6.4 真库欠一版迁移，评测脚本的账本会**静默变空**（2026-09-20）

**症状**：第一次跑 A0 基线（`smoke_agent.py`），报告打出「任务完成率 100% · 轮数 中位 0 ·
0 工具」——**看着像模型一个工具都没调**。实际是一次 INSERT 失败：

```
sqlite3.OperationalError: table turn_traces has no column named sources_injected
```

**为什么会这样**：`turn_trace.finish` 是 **best-effort**（「记账失败绝不能影响已经答完的
那一轮」——那条纪律是对的），所以它只 `log.warning`；而读回账本拿到空 → `rounds=0`、
`tool_calls=[]`。于是「**量不出来**」与「**真的是 0**」在报告里长得一模一样。

**根因**：迁移**只在应用启动时跑**（`main.py` 的 lifespan → `bootstrap` → `migrations.run`）。
脚本自己不触发它，所以「加了新列（P3 的 v15）但后端还没重启过」的那个窗口里，任何往
`turn_traces` 写行的脚本（`turn_eval` 也一样）都会**静默丢账**。

**两处对策（都已落地）**：
- `smoke_agent.py` 跑之前查 `migrations.pending()`：有待跑的直接拦住，并给出两种补法
  （重启后端 / 显式 `migrations.run()`——它会先自动备份）；
- `agent_eval` 多一条 `trace_missing`：账本读不到就是一条 finding + 报告里单独一行，
  **不许把空当成 0 读**。

**判据**：报告里「从账本读出来的数」突然全变 0，先查迁移状态与那条 `log.warning`，
别先怀疑模型变懒了。（与 §6.2「检索失败会被算成 miss」同一族：**量不出来必须响**。）

### 6.5 改了判据想重判，先问「报告里原始事实够不够」（2026-09-20）

**症状的诱惑**：尺子改了（A0 的只读工具白名单收成通则、`one-pager` 加了 `decide`），
最省事的做法是「拿旧报告重算一遍 findings」。这条路**看起来**免费又干净。

**它有一半是断的**：`check_task` 里的 `body_not_in_reply`（成品不许同时摊在对话里）
要**盘上的正文**，而报告里**没有 `bodies`**（`run_tasks` 判完就 `pop` 掉了，`reply`
还截到 1500 字）。拿报告重算那几条，会得到**看起来一样、其实换了输入**的结果——
正是本页反复说的「以为在量、其实没量」。

**边界画在哪**：`agent_findings`（工具白名单 / 该用的工具 / 轮数预算 / 落盘体裁 / 账本）
用的原始事实（`tool_names` / `artifacts` / `rounds` / `trace_missing`）报告里**留全了**，
所以只有这半边能安全重算。`--rejudge` 就是这半边：

```
python smoke_agent.py --rejudge data/agent_baseline.json   # 不调模型，另存一份 .rejudged.json
```

**它的价值不只是省钱**：重跑会让**模型的随机性**混进来（同一批任务，体裁与落盘次数都会变），
而重判把「尺子变了」和「这次手气好」彻底分开；而且两份报告都重判一遍之后
`tasks_sha` 变成同一个（同一把尺），`--compare` 那句「不可比」也就消失了。

**验证方式（照做）**：重判后逐栏比一次原始事实——字段一个都不许动。
2026-09-20 那次：16 条 × 18 栏 = 288 处比对，**0 处不一致**，findings 只变了预期的 2 条。

### 6.6 改列类型要重建表：DDL 从模型长出来，别手写（2026-09-20，Agent A2）

**背景**：A2 把 `agents.tools_enabled`（布尔）升级成 `agents.tool_whitelist`（文本白名单）。
SQLite **没有** `ALTER TABLE ... ALTER COLUMN`，改类型只有一条路：建新表 → 拷数据 → 删旧表 → 改名。

**手写新表 DDL 会分叉**（这次差点就这么写了）：迁移建出来的表和 `create_all` 建出来的表，
NOT NULL / 默认值 / 唯一约束迟早不一样，而「迁移过的库」与「新建的库」结构不一致是那种
**没人会发现**的坏账。做法是让 DDL 同源：

```python
new = Base.metadata.tables["agents"].to_metadata(MetaData(), name="agents_new")
await conn.run_sync(new.create)          # 结构永远等于模型
```

**三个当场撞出来的细节**：

1. **`create_all` 只带 Python 侧默认值时，裸 SQL 的 INSERT 会在 NOT NULL 上炸**——
   非空字符串列要写 `server_default=""`（`models.Agent.tool_whitelist` 就是）；
2. **测试夹具要照实写**：第一版夹具把 `created_at` 写成可空，迁移就在
   `INSERT ... SELECT` 上撞 `NOT NULL constraint failed: agents_new.created_at`。
   真相是 `agents` 从来没进过 v1 那张 `LEGACY_COLUMNS`（它是 `create_all` 建的），
   所以那一列一直是 NOT NULL——**夹具编出一个真库里不存在的场景，再让迁移将就它，是自欺**；
3. **重建之后要验数据一行没丢**：`PRAGMA table_info` 查列、`SELECT` 逐行比旧值
   （尤其旧布尔的映射：`true → ''`、`false → 'none'`——反了就是把用户配好的「这个 agent
   不许用工具」静默变成全开）。见 `tests/test_migrations.py::test_v17_*`。

### 6.7 评测跑一轮，会在**用户自己的账上**留行（2026-09-20，Agent A2）

**症状**：跑一次协作尺子（`smoke_collab_eval.py`），设置页的「用量按事记」里多出几条
用户没做过的协作——`usage_ledger.traced("collab")` 的 `finally` 就是往 `model_usage` 写行。

**对策**：评测跑完**把自己这个窗口里写下的行收走**（开跑前记 `MAX(id)`，跑完删
`id > max_id AND kind = 'collab'`）。**按 id 窗口删、不按 kind 大扫除**：用户自己真跑过的
协作一条都不许动。`agent_eval` 收 `turn_traces` 是同一条纪律（那次是「设置页那栏
『最近回合』里留下 16 条用户没聊过的记录」）。

**判据**：任何新的评测脚本，问一句「它跑起来会往哪张表写东西？那些行归谁？」——
写进用户账本的那些，跑完必须收走，并且**只收自己写的**。

### 6.8 要花钱的抽查，先免费查「这条任务会不会触发你要量的东西」（2026-09-20，Agent A4）

**症状**：A4（把「手头那件事」注入 system）验收里写着「注入前后 A0 抽查」，于是准备挑 3 条
A0 任务跑两臂。**跑之前先花两秒扫了一遍题面**：19 条任务 + 3 条协作任务里，**一条都不含**
A4 的指涉词（`thread_context.REFER_WORDS`）。也就是说那条注入在整轮抽查里**一次都不会触发**
——两臂必然一模一样，而报告会把它印成「注入前后没有差别」。

**这一条比它看上去重要**：那次抽查**不会报错、不会变红**，只会给出一个看起来像结论的
「前后一样」。同族的前科有两次：`--dry` 只查「字段齐不齐」时，16 条任务的 `artifact_kinds`
从来没生效过（§6.5 那次白杀一轮付费）；以及 §6.2「检索失败被算成 miss」——都是**量的东西
不在场，而报告照样出数**。

**对策（两条一起做）**：

1. **抽查前先扫一遍**：这条任务真的会走到你要量的那条路上吗？（一行脚本就够，见
   `continue-recent-thing` 那条任务的 `note` 是怎么写的）；
2. **觉得量不到就改尺子，别硬跑**：A4 最后是**给金标加了一条能触发的任务**
   （`evals/agent/tasks.jsonl` 的 `continue-recent-thing`：题面说「我手头那件事叫什么」，
   而事名只在注入段里出现），再配一条 `validate` 规则拦住「判据在题面/材料里就能看到」的写法
   ——这样那条任务**绿了就等于注入到了模型手里**（名字它猜不出来）。
   探针与量法：`smoke_agent.py --only continue-recent-thing` 与 `--no-inject` 各跑一遍。

**判据**：凡是要花钱的「前后对比」，先免费回答一句「**前面和后面，差别会在哪一栏显示出来**」。
答不上来就先别跑。

### 6.11 判据读的那份文本，可能是**被截断过的报告字段**（2026-09-20 晚，Agent A2 挂账②）

**症状**：fanout 拆成 10 步之后那条任务被判 `missing_marker`，而**每一步都跑成了、产出里也
确实有那些事实**。查下去：`collab_eval.judge` 比 marker 用的是 `result["transcript"]`，
而那是 `run_tasks` 存进报告时**按 `TRANSCRIPT_CAP = 4000` 截过**的字段——4 步时 3~4k 字正好
不截断，10 步之后那一轮产出 **45190 字被截到 4000**，6 个 marker 里 5 个掉在截断外。

**这是 §6.8 的同族**（那一条是「量的东西不在场」，这一条是「判据读的是它的一个残缺副本」），
而且**不报错、不变红**：报告上就是一条理直气壮的 `missing_marker`。

**对策**：判据读**原始事实**（`facts[i].text`，报告里一直留全了），报告里那份截断的纪要继续
只服务人审。**旧报告不用重跑**——全文一直在，`--rejudge` 免费重判就能纠正
（实测 `k3_tools-r1` 那一条当场从 ❌ 变 ✅）。

**判据**：给报告存字段时问一句「**这个字段是给人看的，还是给判据读的**」。
给判据读的字段**不许截断**；两者要的是同一份东西，就存两份（一份全的给判据、一份短的给人审）。

### 6.12 限流/失败会让一次生成**静默换成另一档的行为**（2026-09-22，RAG P1c 委托臂）

**症状**：跑查询策略的委托臂（`smoke_strategy.py --only none,rewrite,rewrite@delegate`）时，
provider 回了 **429 `rpm exhausted`**——因为委托臂每条生成要 2~3 轮（它真会去用只读工具），
而并发仍是给普通档设的 3。

**为什么这是坑而不是"少跑几条"**：委托没走通的那几次，`retriever._delegate_text` 会**退回直连**
（设计如此：这一层是给检索提召回的，不是拿通道换可靠性）。于是那一档的分数里混进了
**另一档的行为**，而分数表**照样打出来**、一行警告都没有——同 §6.2「检索失败被算成 miss」、
§6.8「量的东西不在场」是一族：**失败换了个身份继续进表**。

**对策（三条一起）**：① 委托臂**并发固定 1**（`_DELEGATE_CONCURRENCY`）；② 尺子数
**退回直连的次数**，非零就单独喊一行「这一轮的分数不是干净的委托臂」；③ 单档运行
**不再自己当对照**——`--only rewrite@delegate` 曾经印出一整行「赢 0 / 平 44 / 输 0」，
那看着像结论，其实什么都不是（没有 `none` 就不打配对表）。

**判据**：任何"失败了就悄悄走另一条路"的降级（退回直连 / 退回原话 / 退回默认模型），
**降级次数必须进报告**。不然那张表量的是两件事的混合物，而它看起来像一件事。

### 6.13 `--only` 跑出来的报告，指纹是**那个子集**的（2026-09-22，Agent #4）

**症状**：`smoke_agent.py --only continue-recent-thing` 的报告上印着
`任务集 c25835ab681e`，而金标全集（20 条）的指纹是 `5868ce722928`——**两个数都对**，
但它们说的不是同一件事：`run_tasks` 里那一行是 `tasks_sha(items)`，`items` 是**这一轮真跑的那几条**
（`--only` 已经筛过）。

**为什么这是坑**：`c25835ab681e` 这个数曾经被写进文档当作「20 条金标的指纹」（它其实是那条
A4 任务单跑时的子集指纹）。两个后果：① 拿子集报告当基线去 `--compare`，会得到一句
「不可比」——**对，但理由不是你想的那个**；② 仪表盘那一格读的就是报告里这个数，所以
**一份 `--only` 报告落回默认名，卡片上印的指纹就不再是金标的**。

**判据**：单跑几条（`--only`、A4 那种两臂 drill）**一律用 `--out` 另存**，别写回
`data/agent_baseline.json`；要引用「金标是哪一版」时，用 `agent_eval.tasks_sha(load_tasks())`
**或看整份跑的报告**，别看子集报告上那个数。

### 6.14 两条 A0 评测**不能同时跑**：它们会互删对方种下的那件事（2026-09-22，Agent #4）

**机制**：`agent_eval.run_tasks` 收工时的兜底清理是 `_drop_threads_above(floor)`——`floor` 是
**本进程开跑时** `MAX(Thread.id)`，它删掉**所有 id > floor 的事**。两个进程交错时（A 起、B 起、
A 种 11、B 种 12、A 先收工）→ A 把 11 **和** 12 一起删掉，而 B 那一轮还在跑。

**为什么这是坑而不是"少一条数据"**：B 的注入段里那件事**中途没了**，模型于是答不出「那件事叫
什么 / 到哪一步了」——于是 B 的报告读起来像**功能坏了**（`missing_marker`、去数目录），而不像
跑法错了。同一族：§6.2「检索失败被算成 miss」、§6.8「量的东西不在场」、§6.12「失败换了身份
继续进表」——**失败伪装成了结论**。

**对策**：跑 A0 / 协作这种会往真库写行的评测**一律串行**（写个 `&&` 串起来，或用一条后台命令
依次跑）；要并行就换库。**判据**：动手并行之前先问一句「这个脚本收工时按什么范围删东西」——
按 id 窗口删的，窗口之外的一切都可能是别人的。

### 6.15 阈值扫描表是**样本内最优**：不配交叉验证，它会被读成一个可达目标（2026-09-24，RAG 质量门）

**机制**：`smoke_quality_gate.py` 的「误放率 ≤ 上限时放行率最高能到多少」是在**同一批 63 条**
上从几百条候选规则里取最大。样本只有 39 好 / 24 坏（真正的硬负样本 **10** 条），取最大
天然乐观——**扫出来的差值里有一部分是拟合出来的**。实测代价：把同一族规则放进 5 折 × 20 次
重复（只在训练折上挑、留出折上算），承诺「误放 ≤ 10%」的那一档留出是 **放行 39% / 误放 26%**；
三档**没有一档**在留出上同时赢过那个"拍的、没拟合"的在用运行点（56% / 21%）。

**为什么这是坑而不是"数字不准"**：扫描表读起来像一张**菜单**（"误放 10% 只要 49% 放行，
划算"），于是下一步就是去改阈值——而改完是**真的会变差**，且变差的方向刚好是当初想改善的那一边。
同一族：§6.2「检索失败被算成 miss」、§6.12「失败换了身份继续进表」——**读数伪装成了结论**。

**对策**：① 尺子里**自带**交叉验证（`smoke_quality_gate.py` 末尾那一节，`--cv 0` 可跳过），
扫描表与留出数**并排印**，结论由代码算（"没有一档同时赢过基准"是算出来的，不是写死的）；
② 更一般地：**任何"在某批样本上挑最好"的表，都要问一句"换一批还成立吗"**——
n 小的时候（几十条）答案经常是不成立；③ 真要动运行点，先扩样本（这里最短的一步是
**硬负样本 10 → 几十条**），而不是先调阈值。

### 6.9 临时 vault 有**第二份真值**：只换一份，注入段会安静地少一半（2026-09-20，Agent A4）

**背景**：评测跑在临时 vault 上（`turn_eval._scratch_vault`），做法是把 `mcp.VAULT_DIR`
与 `_VAULT_ROOT` 换成临时目录。而 `core/threads.py` **自己持一份** `VAULT_DIR` 常量——
A4 的注入段正是它解析「这件事挂着哪些引用」时读的那一份。

**只换 `mcp` 的后果**：种下的事指向临时 vault 里的材料，解析却跑到**真 vault** 里找一个不存在
的路径 → 那条引用被标成「已不存在」→ 注入段里少了一整块，**报告上一个异常都没有**。
（`tests/test_agent_orchestration._point_vault` 早就写过同一句话：「两边一旦分叉，挂接会安静地
什么都不做」。）

**对策**：`_scratch_vault` 现在一次换三份（`mcp.VAULT_DIR` / `mcp._VAULT_ROOT` /
`threads.VAULT_DIR`）。**判据**：谁再给「vault 在哪」加一个新的持有者（模块级常量），
就得同时问一句「评测换 vault 的时候，它换了吗」。

### 6.10 那一轮的**自伤**清单（2026-09-20，Agent A4）——不是环境的坑，是我自己的

   会被读成系统变好——而其中一半可能只是"多了一条容易干净的任务"。

## 8. 视觉/布局类改动的验收（2026-10-01 加）

**「看起来没问题」不是验收。视觉类改动同一路由、逐档宽度、换肤前后各量一次，出数字表。**

起因：窄屏版面那轮，改之前以为「24/24 全过」——其实量错了页面（量的不是聊天页）。
横向溢出 65px 这种问题，只有拿数字才藏不住。之后的验收方式：

1. **工具**：起后端（`uvicorn app.main:app --port 8000`，服务的就是 dist），浏览器
   `setViewportSize` 逐档设宽；每档量
   `document.documentElement.scrollWidth > window.innerWidth`（横向溢出）、
   目标元素的 `offsetWidth` / `scrollWidth vs clientWidth`（内部顶没顶出去）、
   关键开关（如图标轨、提示层）的 `getComputedStyle(...).display`。
2. **档位**（对齐本仓真实的窄窗场景——分屏小窗，不是手机）：
   `1440`（基线）→ `900`（图标轨断点）→ `600`（工作区）→ `481`（提示线上）→ `480/375`（提示层）。
3. **换肤前后各一遍**：皮肤改的是 CSS 变量，版面在另一套变量下塌了不算过。
4. **截图留档**：数字表之外，断点两侧（900/880、481/480）各一张，肉眼复核排版。
5. **结论**：一张「宽度 × 指标」的表贴在报告里，超过 1px 的溢出即失败——
   「能打开但横向滚动」是最不该有的中间态。

组件级行为变化（点按钮发生什么）仍归 vitest；这里管的是 vitest 看不见的那一层
（CSS 媒体查询、真实布局、皮肤变量）。
