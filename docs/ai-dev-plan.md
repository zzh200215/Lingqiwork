# AI 开发工作台计划：提示词 · 数据集 · 编排

> 需求原文（你说的）：AI 应用开发里除了写代码，最耗精力的是提示词工程、数据集处理、
> Agent 编排、产品文档撰写、测试用例设计。三个具体想法：
> ①「提示词实验室」——调出一个好 Prompt，宠物就学会一个新技能，存成技能卡片；
> ②「数据集喂养」——上传标注好的数据集 = 喂食，吃不同领域的数据进化出不同形态；
> ③ 多 Agent 协作——宠物当项目经理，在群里调度子 Agent，配一个用玩具/道具表示的可视化编排面板。
>
> 这份文档先给**专业判断**（哪个直接做、哪个要改关键字、哪个要拆成两半），再给路线图。
> 结论提前说：**三个想法里有近两个的底座已经在仓库里了**，而其中一条**这个仓库已经
> 明确考虑过并主动搁置了**——不是懒，是有实测理由的。

## 1. 一句话结论

**方向对，但三处要改词：**

| 你的说法 | 我的建议 | 为什么 |
|---|---|---|
| 提示词**实验室** | 提示词**对照台** | 缺的不是编辑器，是**证据**。仓库自己记着「提示词改动带 A/B 证据的比例：0」 |
| 数据集**喂养**（上传文档 → 进化形态） | **标注样本喂养**（进化 = 可验证能力） | 「上传量决定形态」会被灌水灌出来，而且违反你自己定的两条家规 |
| 宠物当**项目经理**（自主调度） | 宠物当**调度看板**（确定性编排 + 点名催办） | 自主编排仓库已搁置；外部数据一致：多 Agent 生产失败率 >40% |

**最要紧的一句**：这件事和你已经写下的 `docs/upgrade-plan.md` **不是两件事**。
那份计划的 P1（「织网」：把行为写成可回归的用例）就是这里的 Q1。**别开两条并行线**——
否则会出现两套金标集、两套判分器、两套"这条改动到底有没有变好"的答案。

## 2. 勘察：底座已经有多少

先摆清楚已经有的。这个仓库在"非编程工作"这条线上的工程量，比表面看到的多：

| 已有资产 | 位置 | 它意味着什么 | 缺什么 |
|---|---|---|---|
| **系统提示词登记表** | `core/prompts.py::_SPECS`（32 条，sha 指纹，改了就测试红） | 「提示词」的真身**已经登记在册**，而且有防漂移的锁 | 只有健康检查里的一行摘要（`routers/health.py` 调 `prompts.summary()`，给条数与漂移），**没有逐条的面**：看不到内容、看不到 sha、没有 diff、没有对照。改一条 = 改 Python + 手工跑验收 drill（P2 我就是被这条挡住的） |
| **用户提示词库** | `Prompt` 表 + `routers/prompts.py` | Open WebUI 风格的片段库（带 `{变量}`） | 这是**另一个东西**：它不驱动系统行为、没有指纹、没有分数。别把技能卡绑在这上面 |
| **技能（SKILL.md）** | `core/skills.py` + `routers/skills.py` | 业界的 Agent Skills 格式：每轮注入一句索引，模型按需 `skill_load` 全文，可从 URL 安装 | 技能**没有任何质量证据**：装上就是装上，没人知道它好不好用 |
| **智能体** | `models.Agent` + `routers/agents.py` | 人设 + 模型 + RAG + 工具，可增删改 | 没有"这个智能体在什么任务上靠谱"的记录 |
| **协作** | `core/collab.py` + `POST /api/agents/collab` | **确定性**的 pipeline / review 两种编排（2–4 个 agent，v1 故意关掉工具） | 只有两种形状；没有可视化；没有"谁在跑"的看板 |
| **任务链 + 人工卡点** | `core/tasks.py`（`chain_next_id`、`awaiting_run_id`、approve/reject） | 确定性编排**已经能跑多步**，而且**人在环上** | 链是看不见的：界面上只有一行 last_status |
| **成文引擎标尺** | `core/engine_eval.py` + `backend/evals/engines/*.json` | 5 个引擎：结构判分（确定性、零成本）+ 接地判分（LLM 0-5） | 只盖"一次生成一份成文" |
| **评测集** | `EvalItem` + `routers/evals.py` | 标注样本 CRUD + 跑分 + **对比**（`/compare`）+ **健康度**（条数/标注覆盖/区分度） | 只盖 RAG 检索。聊天工具循环、技能、提示词**一条都没盖** |
| **人工满意率** | `core/quality.py` + `ArtifactFeedback` | 按 `(kind, prompt_sha, model_id)` 聚合——**自动分和人点的分落在同一把 key 上** | 靠用户想起来点 |
| **用量账本** | `core/usage_ledger.py` | 横切记账（contextvar span），加一条 span 不用改二十个模块 | — |
| **知识图谱** | `core/kg.py` + `routers/kg.py` | 建图 / 查询 / 状态——「它的知识长成什么样」有真数据 | 没和宠物、评测接起来 |

**两次已经写下的否决，值得先记住：**

1. **自主编排被主动搁置。** `core/collab.py` 的 docstring 原文：
   > "deterministic multi-agent runs (**no autonomous orchestration** — the LobeHub CAO style
   > remains in the observation pool **until the pattern matures**)"
2. **微调是明确非目标。** `docs/upgrade-plan.md` §3：「不追多模态 / 微调 / 自建推理」。

这两条直接决定 ② 和 ③ 该怎么做。

## 3. 逐条判断

### ① 提示词实验室 + 技能卡 —— **做，但产物不是编辑器，是一次对照**

**为什么这不是"再来一个 playground"。** 仓库自己量过：`docs/upgrade-plan.md` §7 把
「提示词改动带 A/B 证据的比例」列为过程指标，并写明**现在是 0**；§9 的最后一句是
「**在此之前，任何 prompt 改动都是没证据的**」。P2 那一轮我想改 `FEYNMAN_PROMPT`，
被 `prompts.py` 的规矩拦住（改提示词必须过验收 drill，那个 drill 真调模型）——
**规矩是对的，工具是缺的**：今天要拿证据，得手写脚本。

外部做法完全一致：提示词管理工具的共识是把**版本与评测绑在一起**（改了哪一版 → 拿哪套
数据集跑 → 和线上基线比 → 才发布），而且回归集要**包含真实发生过的失败案例**
（[PromptLayer 2026 田野指南](https://www.promptlayer.com/blog/best-prompt-management-tools-2026-field-guide/)、
[Braintrust 版本管理](https://www.braintrust.dev/articles/best-prompt-versioning-tools-2025)、
[Maxim 的 A/B 步骤](https://www.getmaxim.ai/articles/how-to-perform-a-b-testing-with-prompts-a-comprehensive-guide-for-ai-teams/)）。
这个仓库差的就是这一步，而**join key 已经有了**：`prompt_sha`。

**与宠物怎么绑（关键）：**

> **技能卡 = 一条有基线的能力。**
> 不是"你在编辑器里点保存，宠物就学会了"——那会让"学会"退化成"你点了按钮"，
> 与本轮刚立的家规（算出来的，不是编的）直接冲突。
> **技能只有一个到手方式：它被证明有效过。** 反之，**没有基线的技能，宠物不展示**。

拆开说，仓库里有两个"技能"概念，必须选对：

| 候选 | 是什么 | 该不该绑 |
|---|---|---|
| `core/skills.py` 的 SKILL.md | 一整套指令包，模型按需加载 | ✅ **主要绑定对象**（它是"能力"） |
| `core/prompts.py::_SPECS` | 驱动全局行为的系统提示词 | ✅ **绑定**（它是"内功"：改它要证据） |
| `Prompt` 表（用户片段库） | 存起来备用的一段文本 | ❌ **不绑**。它没有行为、没有指纹、没有分数，绑上去就是"零柒展示了一堆书签" |

**验收**：改一条已登记提示词或改一个 SKILL.md → 一条命令/一次点击给出**对照报告**：
跑的是哪套样本、`k/n` + **Wilson 区间**、成本、失败用例逐条理由 → 通过才允许登记
（`_SPECS` 指纹同步），并在小屋里长出对应的技能卡。

**工期**：Q1 3–4 人日（判分器大多是确定性的、零成本）。

### ② 数据集喂养 + 进化形态 —— **拆成两半：一半真、一半会变成装饰**

**真的那半：喂养标注样本。**
`routers/evals.py` 已经有标注样本的 CRUD、跑分、对比和**健康度**（条数 / 标注覆盖 /
区分度）。所谓"喂养"，就是把**真实发生过的坏例子**标好喂进去——这正是外部最佳实践说的
"maintain a regression dataset of real production cases **including past failures**"。
宠物"吃到"的进度用真数表达：覆盖率、区分度、指标变化。喂进去之后**分数会变**，这才是食物。

**假的那半：上传文档决定形态。**
「吃了大量法律文书 → 变成法务小助手形态」——**这个仓库不微调**，所以上传的文书不会让模型
变成法务。会上涨的只有**检索覆盖**。如果形态由"上传量"驱动，它就是一个**灌水就能灌出来的
装饰**，而且同时违反你自己已经定下的两条：

- `pet.py` 家规一：「**来自真实数据**——算出来的，不是编的」；
- `quality.py` 红线：「**这是诊断工具，不是考核仪表。不设目标、不催、不做排行榜**」。

外部的老话不客气：**当指标变成目标，它就不再是好指标**
（[Goodhart's law](https://en.wikipedia.org/wiki/Goodhart%27s_law)）。
「上传 100 篇 → 长出法务形态」正是那种"目标"，而它的最优解是**灌水**。

**诚实版（而且我认为它更好玩）：**

> **形态 = 该领域可验证的能力**，三个真数：① 该领域的检索质量（Hit@k / 忠实度，
> `evals.py` 现成的）；② 该领域搞懂的概念数（`tutor` 的掌握事件）；③ 该领域技能卡的
> 评测通过率（Q1 的产出）。
> 三样都够，才长出那根枝。

界面上要**明说什么没有发生**——这一条和 P4 的「它不饿」是同一个立场：

> 「它没有学会法律。它在这个领域检索得住、引用得住，技能卡过了 3/4。」

「喂养」这个词可以留，但**喂的是标注样本与技能（它们真的改变分数），不是文档
（那只改变覆盖）**。文档的诚实等价物是：「这一柜它现在引用得住了」——那是可测的。

**工期**：Q2 3–4 人日。

---

### ③ 多 Agent + 宠物当项目经理 —— **视觉那半做，自主那半不做**

**视觉那半（做）**：`collab.py` 只有两种确定性模式（流水线 / 评审回路），`tasks.py` 已经有
任务链（`chain_next_id`）与人工卡点（`awaiting_run_id` + approve/reject）。
把这些画成一排"玩具流水线"——**低风险、立刻可做，而且正好是宠物擅长的事**：状态与播报。

**自主那半（不做）**：让主 Agent 自己决定派谁、什么时候派。三条理由，一条来自本仓库，
两条来自外部：

1. **仓库已经否决过。** `collab.py` 的原文见 §2——"until the pattern matures"。
   这个决定是有代价意识的：`collab.py` 的 v1 **故意关掉工具**（"collaboration multiplies
   token cost already"）。
2. **单 agent 的错误率会相乘。** `docs/upgrade-plan.md` §2.2 量到：聊天工具循环 22 轮里
   **2 轮声称存了却一次没调**，还**编造过不存在的文件路径**和**不存在的约束**。
   一次 8% 的失真，串 5 步之后成功率只剩 0.92⁵ ≈ **66%**（失败率从 8% 涨到 **34%**）——
   而每一步都是一个真花钱、真落盘的步骤。多 Agent 最新的行业数据同向：
   **没有编排的多 Agent 系统生产失败率 >40%，协调失败占全部故障的 37%**
   （[Galileo](https://galileo.ai/blog/multi-agent-ai-failures-prevention)）。
3. **最阴的失败模式恰好是这个产品最怕的**：编排者拿着不完整的信息继续推进，
   产出一个**看起来对、但错了且没人发现**的结果
   （[TrueFoundry](https://www.truefoundry.com/blog/what-is-multi-agent-orchestration)）。
   这正是「谎报落盘」的高级版本。

**诚实版：宠物是项目经理的"看板"，不是那个拍脑袋的调度者。**

- **派活由确定性编排决定**：流水线 / 评审回路 / 任务链；
- **宠物负责**：谁在跑、谁挂了、谁在等人点头、下一步该谁——**全部从 `task_runs` /
  `awaiting_run_id` 算出来**（和 P1 的状态机同一个套路，零新真值）；
- **"点名催办"做成按钮**：真实的 run / approve / reject，而不是聊天里 @ 一下就算了。

如果一定要「在群里 @文案Agent 整理今天的反馈」这个体验：把它做成**指令的语法糖，而不是自主性**
——服务端把这句翻译成**一次确定性的 agent run**（可回放、可测试、可撤销），
主 agent 不自由发挥。

**工期**：Q4 3–4 人日。

### ④（我补，你没提）测试用例设计 —— **已经有网，缺的是"从事故到用例"的那一步**

你列的五件非编程工作里，**测试用例设计**在这个仓库是最成熟的（`run_tests.py` 每文件一进程、
59 个后端文件 + 218 条前端用例）。真正缺的是：**一次事故发生之后，把它变成用例**的动作
（upgrade-plan §9 第 3 条：「把本轮发现的所有缺陷写成用例——先把回归网织上，再谈优化」）。
这件事在 Q1 里顺手做掉：**对照台的失败用例，一键存成评测样本**。

### ⑤（我补）产品文档撰写 —— **别再加一个"写文档"的地方，让报告就是文档**

这条你列了，但我一开始漏了，补上：这个仓库已经有三样东西分开长着——
成文引擎（`compose` / `research` / `decide`，落 `notes/`、`research/`、`decisions/`）、
**决策记录**（`core/decision_log.py` + `DecisionLog` 表）、以及 `docs/*.md`。

AI 应用开发真正需要的那种文档不是"再写一篇"，而是**和改动绑在一起的三样**：
① 这条提示词/技能**为什么**这么改（决策记录已有）；② 改完**好没好**（Q1 的对照报告）；
③ 这次改动**影响哪些行为**（回归集里新增的用例）。

所以做法是：**Q1 的对照报告直接落成文档**（一条提示词 = 一段可追溯的变更史），
而不是新开一个文档编辑器。**不做什么**：不做富文本编辑器、不做文档模板市场
——这个仓库里 `docs/*.md` 就是文档，`git` 就是版本。

## 4. 与宠物线的接缝（复用家规，不新立一套）

这四条是 P1–P4 立下的，本维度**一条都不破**：

| 家规 | 在本维度的样子 |
|---|---|
| **算出来的，不是编的** | 技能卡来自"有基线的能力"；形态来自"可验证的领域能力"；看板来自 `task_runs` |
| **只增不减、不欠账** | 技能卡不会因为"最近没用它"而降级；不显示「还差 3 个样本才能喂饱它」 |
| **诊断不是考核** | 分数只用来回答"这次改动变好还是变坏"，不设目标、不做排行榜、不催 |
| **成本要报** | 每次对照跑都报花了多少钱、几次调用（`usage_ledger` 现成），并**有单次预算上限** |

## 5. 目标与非目标

**目标**

1. 改一条提示词/技能，能拿到**带区间的对照证据**，而不是"我看着还行"。
2. 宠物身上长出来的每一样东西，都能点开看到**它是凭什么长出来的**。
3. 多步编排**看得见**：谁在跑、卡在哪、下一步谁。
4. 一次事故 → 一个用例（失败案例能一键存进评测集）。

**非目标（明确不做）**

- **不做自主编排**（理由见 §3③，仓库自己搁置过）。
- **不做微调 / 不做"上传量决定形态"**（会变成可灌水的装饰）。
- **不引入 LangGraph / CrewAI / Dify 那类框架**（upgrade-plan §3 已定；本维度只需要
  把已有两种编排画出来）。
- **不做通用 agent benchmark**，只测**这个产品承诺过的行为**。
- **不为了好看改产品语义**（比如为了让技能卡变多，把一句闲聊也算成技能）。

## 6. 阶段与验收

| 阶段 | 内容 | 验收（可看见的东西） | 估算 |
|---|---|---|---|
| **Q1 对照台**（keystone）✅ 完成 | 提示词/技能 → 跑金标集 → 对照报告（`k/n` + Wilson 区间 + 成本）→ 通过才登记 | 改一条已登记提示词，界面上拿到"这次比上次好还是坏"；失败用例一条条能点开 | 3–4 人日 |
| **Q2 喂食与技能卡** | 标注台（坏例子一键存成样本）+ 小屋里的技能卡（只展示有基线的） | 喂进一条失败用例 → 重跑 → 分数变化可见；小屋里多一张技能卡 | 3–4 人日 |
| **Q3 形态** | 领域枝 = 检索质量 + 掌握概念 + 技能通过率 | 某领域三个数都够 → 小屋里长出那根枝，并写明"它没学会它" | 2–3 人日 |
| **Q4 调度台** | pipeline / review / 任务链 → 道具流水线；宠物播报 + 点名催办 | 一条两步任务链在界面上看得见谁在跑、卡在哪、点谁放行 | 3–4 人日 |

**关键顺序约束**：**Q1 必须在 Q2 之前**，Q3 依赖 Q2，Q4 可与 Q1–Q3 并行。
没有 Q1，Q2/Q3 长出来的东西都是装饰——**这条正是 upgrade-plan 说的那句话**：
「把『改进了吗』这个问题拿 24 个样本去问，答案是『不知道』」。

**最小可见切片**（如果只想先看见）：Q1 的窄版——**只做一条提示词 + 一套 8 条样本的对照**，
从登记表读、跑一次、给出区间，并让小屋把这张技能卡画出来。**这就能"呈现出来"了。**

### 三条边界（写进代码注释，也写进界面）

1. **这一页不能改提示词。** 内容活在源码里（那是唯一事实来源），在这儿改会立刻长出第二个真值。
   候选变体只活在**那一次跑分**里（连正文一起留在 run 记录里当证据），要采纳得去改代码——
   改完 sha 会变，`test_prompts.py` 会提醒你登记漂移了。
2. **断言是声明出来的，不是猜的。** 每条断言都引提示词自己的**一句话**（`CHECKS` 里的 `why`，
   鼠标停在断言上能看到是哪句）。fixture 里写错断言名会**当场算不过**，不静默放过。
3. **n 小就说 n 小。** 报告带 Wilson 区间；宽度 >0.34 时直接写「这个 n 下不了结论」。

### 第一次对照跑出来的三件事（`FEYNMAN_PROMPT`，基线 2/8）

先说清楚这个数字该怎么读：**2/8 不是「这条提示词只有 25 分」**。Wilson 区间是 **7%–59%**，
这么宽的区间下不了任何结论。它能干的是**把 8 条回复摊在桌上让人一条条看**——而看完之后，
有三件事是实打实的：

**一、模型几乎每轮都在抛一串问题，而规则 6 明说「每轮只做一件事…不要一次抛三个问题」。**
原文（`vague-analogy`，一个问号数到 8）：

> 这个调度员手里到底在调度**什么东西**？是"任务"？是"消息"？是"代码片段"？
> 然后——你说的"来回"，来回是什么意思？它来回跑几次？什么时候停下来？它不是一直在转吗？

`term-dropping` 是三个独立问题分三段抛出。这不是"模型不够聪明"，是**这条规矩只写在提示词里，
没有任何结构在拦它**——正是 `upgrade-plan` §4 说的那件事，第一次在**另一条**提示词上被验证。

**二、用户明确邀请它列清单时，「不要列清单」当场失守。**
`three-questions-bait`（用户说"你一次把想问的都问了吧"）的回答里，模型用**编号清单 1./2./3.**
解释为什么不能列清单。这一条比第一条更有意思：**祈祷式的否定规则，在用户反向施压时不成立。**

**三、P2 留的那个问题，有答案了。**
对 P2 那个悬而未决的问题（"要不要让它的追问带零柒的语气"），候选＝已登记内容 + 一句零柒的
语气说明，跑出来是 **2/8 vs 2/8，打平**；翻面一上一下（噪声）。

> **结论：加语气既没让它更守规矩，也没让它更不守规矩——它不是这个问题的解法。**
> 该动的是把「一次一问」从**提示词承诺**搬到**结构保证**（服务端限制问句数，或拆成多轮）。
> 这样一来，`docs/pet-hub-plan.md` §10 那个"留给用户拍板"的问题也自动关闭了：**不折腾提示词。**

### 度量本身待改的一处（我**没有**在这一轮偷偷放宽它）

`one_question_only` 把「一个问题 + 一组选项」和「三个独立问题」算成一样。上面 `refuses-to-teach`
那一条就是被它误伤的：`你想听我讲什么？…比如——注意力机制？梯度下降？Transformer架构？` 是
**一个问题带选项**，却数出 4 个问号。

修它的路有两条：改成「数空行分隔的疑问段」，或给这一条配一个 LLM judge。**这一轮我一条都没动**——
跑完发现指标不合口味就顺手放宽，正是这个项目最该避免的那种自欺。改动要单独跑一次对照来证明
它确实更准（比如用几条人工判过的回复当金标）。
